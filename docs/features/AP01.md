# AP01 — Leitlinien für Coding-Agenten

Stand: 2026-11-06
Ausgangscommit: `8b2cc3f`
Arbeitsbranch: `feature/ap01-coding-agent-guidelines-final`

## Ziel

Die verbindlichen Vorgaben für Coding-Agenten werden um drei Aspekte
erweitert:

- **KISS** als verpflichtendes Prinzip: die einfachste Lösung, die das
  Problem vollständig löst.
- **Clean Code** als verbindlicher Code-Stil.
- **Caching** als Performance-Optimierung, aber nur mit einer definierten
  Invalidierung.

Die Regeln gelten für neue und bestehende Projekte. Neue Projekte erhalten sie
über die Vorlagen; bestehende Projekte übernehmen sie automatisch, ohne dass
ihre eigenen Inhalte überschrieben werden.

## Fachliche Umsetzung

Der verwaltete Block `<!-- vibe:general-rules -->` enthält jetzt drei
Abschnitte:

1. `## Projektordner sauber halten`
2. `## Ordnung im Git halten`
3. `## Leitlinien für Coding-Agenten (verbindlich)`

Der neue Abschnitt legt fest:

- KISS ist verpflichtend; spekulative Abstraktionen, Funktionen oder
  Optimierungen auf Vorrat und Komplexität ohne belegten Bedarf sind
  unzulässig.
- Clean Code ist der verbindliche Code-Stil: sprechende Namen, kleine
  Funktionen mit einer klaren Aufgabe, explizite Schnittstellen, keine
  unnötige Duplizierung und nachvollziehbare Fehlerbehandlung. Verhalten wird
  durch Tests abgesichert, nicht durch Kommentare.
- Caching ist eine begründete Performance-Optimierung und nur mit
  funktionierender Invalidierung zulässig. Jeder Cache braucht einen
  eindeutigen Schlüssel, eine definierte Lebensdauer und eine benannte
  Invalidierung (Zeit, Änderungsereignis oder Version). Ohne korrekte
  Invalidierung wird nicht gecacht. Sicherheits-, Berechtigungs- und
  Geheimnisdaten werden nicht ungeprüft zwischengespeichert.
- Die Leitlinien gelten für alle neuen und bestehenden Projekte unabhängig
  vom Projekttyp.

### Neue Projekte

`vibe new` und `vibe init` kopieren die Vorlagen mit dem vollständigen
verwalteten Block. Zusätzlich setzt `ensure_general_rules` den Block auch für
Vorlagentypen durch, deren `AGENTS.md` ihn nicht bereits enthält.

### Bestehende Projekte

- `vibe init` ersetzt einen vorhandenen, vollständig abgeschlossenen
  Regelblock durch den aktuellen Stand. Inhalte außerhalb der beiden Marker
  bleiben unverändert.
- `vibe run` bringt den Block unmittelbar vor dem Start eines Agentenlaufs auf
  den aktuellen Stand. Damit liest der Agent in diesem Lauf bereits die neuen
  Leitlinien, auch wenn das Projekt zuvor nur mit einer älteren vibe-Version
  vorbereitet wurde. Der Weg über den Startbefehl gilt auch für Läufe aus der
  Weboberfläche, weil sie `cmd_run` aufrufen.
- Kann der Block nicht aktualisiert werden (zum Beispiel wegen fehlender
  Schreibrechte), bricht `vibe run` mit einer verständlichen Meldung ab und
  startet keinen Agenten. Die Leitlinien sind verpflichtend und werden nicht
  stillschweigend ausgelassen.
- Ein unpaariger Marker, eine nicht als UTF-8 lesbare Datei oder ein Symlink
  bleiben unangetastet. Es wird nie außerhalb des Projekts geschrieben.

### Pflichtprüfungen

```
$ bash scripts/verify.sh quick
OK: 53 Dateien stimmen mit docs/import-manifest.json überein.
OK: 83 Python-, 8 Bash- und 4 JSON-Datei(en) syntaktisch geprüft.
OK: keine Geheimnisse erkannt.
OK: Prüfung 'quick' erfolgreich. (Exit 0)
```

Der vollständige Lauf ist grün. Diese Agentensitzung läuft selbst in einem
vibe-Lauf und erbt deshalb `SANDBOX=on`; ihr `/tmp` ist schreibgeschützt und
die Läufer-Tests verwenden feste `/tmp`-Pfade. Der Lauf wurde deshalb in einer
Bubblewrap-Umgebung mit beschreibbarem `/tmp` und ohne geerbte
`SANDBOX`-Variable ausgeführt:

```
$ bwrap --dev-bind / / --tmpfs /tmp -- bash -c \
    'mkdir -p /tmp/vibe-tmp && env -u SANDBOX TMPDIR=/tmp/vibe-tmp bash scripts/verify.sh full'
...
Ran 863 tests in 112.873s
OK
Ran 58 tests in 49.552s
OK
OK: Tests erkannt: 921 (Minimum 1).
OK: Prüfung 'full' erfolgreich. (Exit 0)
```

`env -u SANDBOX` entfernt nur die aus der Agentensitzung geerbte Variable; die
Projektdateien und der Prüfbefehl bleiben unverändert. Ohne diese Trennung
starten die Läufer-Tests ihre Attrappen nicht, weil sie die geerbte
Sandboxkonfiguration als Projektkonfiguration sehen. Derselbe Lauf ohne
Bubblewrap scheitert an den festen `/tmp`-Pfaden der Läufer-Tests und an
`SANDBOX=on`; das ist eine Eigenschaft der Prüfumgebung, nicht des
Arbeitspakets.

## Grenzen

- Die Leitlinien sind verbindliche Anweisungen an die Agenten. Es gibt keine
  statische Analyse, die KISS, Clean Code oder eine korrekte
  Cache-Invalidierung technisch erzwingt.
- Eine nicht beschreibbare `AGENTS.md` verhindert einen Agentenlauf, statt die
  Leitlinien stillschweigend zu übergehen.
- Die Repository-`AGENTS.md` liegt außerhalb der Manifest-Bereiche und wird
  deshalb nicht über die Importprüfsumme abgesichert (wie bereits bei V-022).
- Bestehende Projekte übernehmen die Leitlinien beim nächsten `vibe init` oder
  `vibe run`; ein eigener globaler Migrationsbefehl wurde nicht eingeführt.
