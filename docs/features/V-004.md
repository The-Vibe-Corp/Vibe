# V-004 — Web-API absichern und Health-Endpunkt ergänzen

Stand: 2026-10-26
Ausgangscommit: `b471b08`
Arbeitsbranch: `feature/f8-feedback-abgeschlossen`

## Ziel

Das Dashboard ist eine lokale Weboberfläche. Auch wenn es nur an Loopback
lauscht, darf eine fremde Webseite im selben Browser keine schreibenden
Aufrufe auslösen, und ein fremder Dienst auf dem Port darf nicht für vibe
gehalten werden. Dieses Paket sichert den Transport der Web-API zentral ab:
Bindung nur an Loopback, Tokenpflicht, Host-/Origin-Prüfung, begrenzte
Request-Größen, strukturierte Fehler, tokenfreie Logs und einen
öffentlichen Health-Endpunkt zur Instanzprüfung.

## Lieferumfang

- `bin/vibe-web.py` — zentrale Prüfung `_guard()`, `_authorized()`,
  `_read_json()`, `_health()`; strukturierte Fehler über `_error()`; 1-MiB-Limit;
  private Token-/Instanzdateien; tokenfreies Zugriffslog; Bindungsprüfung über
  `VIBE_UI_BIND`.
- `bin/vibe-web.py` (Frontend) — `api()` liest auch strukturierte Fehler
  (`error.message`) und zeigt sie verständlich an.
- `tests/unit/test_web_api_security.py` — 22 Tests gegen einen echten,
  isoliert gestarteten Dashboard-Prozess.
- `docs/baseline.md` — Webserver-Sicherheitsstatus und API-Routen aktualisiert.
- `docs/import-manifest.json` — Größe/Prüfsumme von `bin/vibe-web.py` und
  Eintrag `V-004` unter `aenderungen`.

## Verhalten

### Bindung und Health

| Prüfung | Umsetzung |
| --- | --- |
| Nur Loopback | `VIBE_UI_BIND` akzeptiert nur IPv4-Loopback (Standard `127.0.0.1`). `0.0.0.0`, Hostnamen außer `localhost` und IPv6 werden mit Meldung und Exitcode ≠ 0 abgelehnt; dabei entsteht keine Token-Datei. |
| Health | `GET /api/health` ist ohne Token lesbar, prüft aber den `Host`-Header. Antwort: `ok`, `app: "vibe"`, `api: 1`, `instance`, `bind`, `port`, `pid`, `started`. Kein Token, kein Token-Wort, keine Pfade mit Geheimnisnähe. |
| Instanzkennung | `INSTANCE = secrets.token_hex(8)` pro Prozess; zusätzlich in `_logs/web.instance` mit Rechten `0600` (soweit das Dateisystem dies zulässt). Zwei Health-Aufrufe derselben Instanz liefern dieselbe Kennung. |

### Authentisierung und CSRF

- Jede API-Route außer `/api/health` verlangt ein gültiges Token per
  `X-Token`; fehlendes oder falsches Token ergibt `403` mit
  `error.code = "unauthorized"`.
- `t` im Query-String wird nur noch für `/api/stream` akzeptiert, weil
  `EventSource` keine eigenen Header setzen kann. Alle anderen Routen lehnen
  den Query-Token ab, damit er nicht in Verlauf, Referern oder Logs landet.
- `Host` muss ein Loopback-Name sein (`127.0.0.1`, `localhost`, `[::1]`,
  Port optional). Sonst `403 forbidden_host`.
- Schreibzugriffe (`POST`) prüfen zusätzlich `Origin`: Schema `http`,
  Loopback-Host und – falls angegeben – den eigenen Port. Ein vorhandener
  `Sec-Fetch-Site`-Header muss `same-origin` oder `none` sein. Sonst
  `403 forbidden_origin`. Damit löst eine fremde Webseite keine schreibenden
  Aufrufe aus, selbst wenn sie das Token nicht kennt und der Browser die
  Anfrage sendet.

### Requestformat und Limits

| Fall | Antwort |
| --- | --- |
| `Content-Type` nicht `application/json` | `415 unsupported_media_type` |
| `Content-Length` fehlt | `411 length_required` |
| `Content-Length` keine Zahl oder negativ | `400 invalid_length` |
| Body größer als 1 MiB | `413 request_too_large`, Body wird nicht gelesen, Verbindung geschlossen |
| Body kürzer als angekündigt | `400 incomplete_body` |
| Ungültiges JSON | `400 invalid_json` |
| JSON ist kein Objekt | `400 invalid_request` |
| Leerer Body | wird als `{}` behandelt (bestehende Aufrufe bleiben gültig) |

Alle Fehler haben die Form:

```json
{"ok": false,
 "error": {"code": "unauthorized", "message": "Token fehlt oder falsch"},
 "message": "Token fehlt oder falsch"}
```

`message` bleibt für bestehende Aufrufer erhalten; `error.code` ist die
maschinenlesbare Kennung. Fachliche Ablehnungen einer Route behalten ihre
bisherige Form und erhalten zusätzlich `error.code = "rejected"`.

### Logs und Geheimnisse

- `log_request()` schreibt nur Methode und Pfad ohne Query-String nach
  `stderr`. `log_message()` bleibt abgeschaltet, damit weder Header noch
  Fehlertexte mit Token in Standardlogs gelangen.
- Das Startkommando nennt den Pfad der Token-Datei, nicht das Token.
- `_error()` und fachliche Meldungen laufen durch `redact()`; das Token wird
  durch `[entfernt]` ersetzt, falls es je in einer Meldung auftaucht.
- Token- und Instanzdatei werden mit `0600` geschrieben; auf FUSE/NTFS kann
  das Dateisystem diese Rechte nicht durchsetzen (siehe Grenzen).

## Tests

`tests/unit/test_web_api_security.py` startet `bin/vibe-web.py` mit
temporärem `VIBE`, `HOME` und freiem Port und prüft:

- Health ohne Token, stabile Instanzkennung, Loopback-Bind, Port, PID und dass
  das Token nicht in der Antwort steht.
- Health und Schreibzugriffe mit fremdem `Host` (`vibe.example`,
  `127.0.0.1.evil.example`, `192.0.2.10`).
- Fehlendes Token, falsches Token, Token im Query-String bei normalen
  Lesezugriffen sowie ein Token mit Nicht-ASCII-Zeichen im Header und im
  Query-String von `/api/stream` (strukturierte `403`, kein Verbindungsabbruch).
- Fremder `Origin` (auch anderer Loopback-Port, portlos oder `https`), fremder
  `Host`, `Sec-Fetch-Site: cross-site`; jeweils ohne
  Zustandsänderung. Gegenprobe: gleicher Origin plus Token wird akzeptiert.
- Ungültiges JSON, JSON-Array, fehlender/falscher Content-Type, fehlende
  Content-Length und angekündigte Größe über 1 MiB.
- 24 parallele Lesezugriffe und 12 parallele Schreibzugriffe mit gemischter
  Autorisierung; jede Anfrage wird einzeln richtig bewertet.
- Zugriffslog enthält den Pfad, aber weder Token noch `t=`.
- Start mit `VIBE_UI_BIND=0.0.0.0` wird abgelehnt und schreibt keine
  Token-Datei.

## Bekannte Grenzen

- Der Server spricht HTTP/1.0 und beendet die Verbindung nach jeder Antwort.
  Das ist für das lokale Dashboard ausreichend; Keep-Alive ist kein Ziel.
- Das Body-Limit betrifft den Request-Body. Die Header-Größe wird nicht
  separat begrenzt; es gilt die Grenze der Standardbibliothek.
- Es gibt kein Rate-Limit und keine Begrenzung gleichzeitiger Threads. Die
  Loopback-Bindung und die Tokenpflicht sind die primären Schutzgrenzen.
- Ein Token gilt für die gesamte Instanz; es gibt keine Benutzer oder Rollen.
- `0600` auf Token-/Instanzdatei ist auf FUSE/NTFS nicht garantiert. Die
  Laufzeitdaten müssen auf einem geeignet geschützten Dateisystem liegen.
- Der Health-Endpunkt ist absichtlich ohne Token lesbar, damit ein Starter die
  Instanz prüfen kann. Er gibt keine Geheimnisse aus und ist nur über
  Loopback erreichbar.
- Die fachlichen API-Routen wurden durch dieses Paket nicht neu getestet;
  geprüft ist der gemeinsame Transport. Offene Fachthemen bleiben in V-005,
  V-009, V-012 und V-013.
