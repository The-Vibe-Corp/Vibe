## Fehlerbild

Der Eintrag B13 lautet wörtlich:

```
- [ ] B13 Anweisung senden gitb Fehler
  Art: Bug
  Beschreibung: Wenn ich eine Anweisung an einen Agenten senden möchte erhalte ich folgende Fehlermeldung:
  "Der opencode-Server ist nicht erreichbar: [Errno 111] Connection refused"

  Erwartet: Das alles notwendige (sowohl für opencode/pi) automatisch eingestellt ist und die funktion einsatzbereit ist.
```

Eine Zusatzanweisung aus dem Dashboard (F19, `POST /api/steer`) wurde mit
„Der opencode-Server ist nicht erreichbar: [Errno 111] Connection refused“
abgelehnt. Ursache: Läufe ohne erreichbaren gemeinsamen opencode-Server
starteten mit `--standalone`. Die Agentensitzung lebte dann ausschließlich im
Agentenprozess; das Dashboard hatte kein adressierbares Ziel und konnte die
Anweisung nicht zustellen. Ein gemeinsamer Server ist nicht überall vorhanden
— insbesondere nicht in der Sandbox, die den Agenten samt Werkzeugen in einem
bubblewrap-Prozess hält.

### `bin/vibe-run.sh`

- **Start:** Der Läufer startet bei Bedarf `opencode serve --hostname
  127.0.0.1 --port <freier Port>`. Den Port ermittelt ein kurzer Python-Aufruf
  über einen an Port 0 gebundenen Socket. Das Kennwort kommt ausschließlich
  über die bereits aus der bestehenden Kennwortdatei exportierte
  Umgebungsvariable `OPENCODE_SERVER_PASSWORD`; bei den opencode-Aufrufen
  steht es weder in der Argumentliste noch in der Serverdatei oder im
  Laufprotokoll.
- **Sandbox:** Ist `SANDBOX=on`, läuft der Server innerhalb desselben
  Sandbox-Wraps (`python3 bin/vibe_sandbox.py <Projekt> --`). Ein gemeinsamer
  Server außerhalb der Sandbox würde Werkzeuge ungeschützt ausführen.
- **Gesundheitsprüfung:** Vor dem ersten Agentenaufruf prüft der Läufer
  `GET /api/info` mit Basic-Auth und Zeitlimit (bis zu 15 Sekunden). Erst ein
  gesunder Server erhält seine Übergabedatei. Bleibt der Server ungesund,
  bricht der Lauf ab; es startet kein Agent gegen einen toten Server, und
  `--standalone` wird nicht stillschweigend als Ersatz verwendet.
- **Kennwort der Gesundheitsprüfungen:** Die Prüfungen rufen curl wie der
  bisherige gemeinsame Server-Pfad auf und übergeben das Kennwort als Argument
  `-u opencode:<Kennwort>` (vorbestehend seit B3, `CURL_AUTH`). Dadurch liegt
  es kurzzeitig in `/proc/*/cmdline`. Das ist übernommenes Altverhalten und
  keine B13-Regression. Die Geheimhaltungsassertionen der B13-Tests decken
  opencode-Argumente, Serverdatei, Protokolle und Läuferausgabe ab, nicht
  curl-argv.
- **Wiederverwendung:** Zwischen Paketen prüft `private_server_healthy()` den
  zuletzt geschriebenen Loopback-Endpunkt. Ein gesunder Server wird
  weiterverwendet; nur ein fehlender oder nicht mehr gesunder Server führt zu
  einem Neustart.
- **Übergabedatei:** `<Laufprotokoll>.server.json` enthält `url`, `port` und
  `password_file`. Das Dashboard liest daraus Ziel und Kennwortdatei. Die
  PID-Datei `<Laufprotokoll>.server.pid` dient ausschließlich dem Aufräumen.
- **Serverausgabe:** Die Ausgabe des Servers geht nach
  `<Laufprotokoll>.server.log` und nicht in das Laufprotokoll.
- **Laufende:** Der EXIT-Trap beendet den Server samt Prozessgruppe (TERM,
  danach KILL) und entfernt Serverdatei und PID-Datei. Mehrfache Aufrufe sind
  unschädlich.
- **Aktive Bedingungen:** Der private Server wird nur gestartet, wenn alle
  drei Bedingungen gelten: Harness `opencode`, eine nichtleere Kennwortdatei
  und (Sandbox an **oder** kein erreichbarer gemeinsamer Server). Eine Datei
  aus Leerzeichen gilt wie eine fehlende.
- **Unverändert:** Pi-Läufe starten keinen privaten Server (AK7). Ein
  erreichbarer gemeinsamer Server behält das bisherige `--server`-Ziel (AK9).

### `bin/vibe-web.py`

- `steer_server_url()` akzeptiert ausschließlich Loopback-Ziele über HTTP mit
  gültigem Port (`127.0.0.1`, `localhost`, `::1`). Andere Schemata, fremde
  Hosts und ungültige Ports liefern `None`.
- `steer_endpoint(name)` liest `<Laufprotokoll>.server.json` des Projekts.
  Nur eine gültige Loopback-URL wird angenommen; das Kennwort wird aus der
  dort genannten Kennwortdatei gelesen. Ist sie nicht lesbar, greift wie
  bisher die gemeinsame Kennwortdatei.
- Fehlt die Serverdatei, ist sie defekt oder nennt sie ein fremdes Ziel,
  bleibt der bisherige Pfad zum gemeinsamen Server unverändert (Rückfall).
- `deliver_steer(target_url, session, text, password)` arbeitet jetzt mit
  einem parametrisierten Ziel. Die bisherige Prüfung (gültige Basic-Auth,
  Erfolg nur bei 2xx, kein Kennwort in Antworten) bleibt bestehen.
- Die Pi-Ablehnung und die Session-Prüfung von `steer_project()` sind
  unverändert.

### `tests/unit/runner_support.py`

Die opencode-Attrappe erhielt einen `serve`-Zweig (`_b13_serve`): ein
minimaler HTTP-Server mit Basic-Auth-geprüftem `GET /api/info`, einem
Beobachtungsprotokoll (`FAKE_SERVE_RECORD`), einer Verzögerung
(`FAKE_SERVE_DELAY`) und der Variante „lauscht nie“ (`FAKE_SERVE_NEVER`).
Bestehende Aufrufpfade (`run`, Preflight, Paketabschluss) sind unverändert.

## Bekannte Grenzen

- **Vorbestehender Umgebungsfehlschlag:** `test_sandbox.SandboxCommandTest.
  test_real_sandbox_allows_write_dirs_and_denies_unlisted_paths` schlägt
  ausschließlich dann fehl, wenn `TMPDIR` unter `/tmp/opencode` liegt. Die
  Sandbox bindet `/tmp/opencode` als Standard-Schreibverzeichnis ein; das
  Fixture-HOME liegt dann darin. Mit `TMPDIR=/tmp` ist der Test OK. Der
  Fehlschlag ist nicht B13-bedingt und im Testbericht belegt.
- **Pi:** Pi-Läufe unterstützen weiterhin keine Zusatzanweisungen; daran
  ändert B13 nichts (F20).
- **Serverausfall mitten im Lauf:** Stirbt der private Server nach bestandener
  Gesundheitsprüfung, liefert die Dashboard-Zustellung weiterhin die
  Rohtechnikmeldung „Der opencode-Server ist nicht erreichbar: [Errno 111]
  Connection refused“. Verständliche Fehlertexte sind mögliche Folgearbeit.
  Es gibt keinen Autorestart-Anspruch; der Lauf wird dadurch nicht
  stillschweigend als erreichbar ausgegeben.
- **Port-Freimessung (TOCTOU):** Der private Port wird vor dem Serverstart
  freigemessen. Belegt ein anderer Prozess ihn zwischenzeitlich, bricht der
  Lauf nach 15 Sekunden Gesundheitswarten mit verständlicher ABBRUCH-Meldung
  ab (korrekter Abbruch, keine stille Fehlfunktion). Beim nächsten Lauf wird
  ein neuer Port freigemessen; Selbstheilung ist damit gegeben.
