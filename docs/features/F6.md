Stand: 2026-10-26

Arbeitspaket: FEEDBACK.md, Eintrag F6

## Ziel

vibe soll auf einem neuen Rechner ohne manuelles Kopieren einzelner Dateien
installierbar sein. Der Setup

- läuft interaktiv und erkennt Linux (Ubuntu/Debian, Fedora, Bazzite),
  Container (Docker/Podman/Toolbx/Distrobox) und Windows,
- prüft die benötigten Werkzeuge und schlägt konkrete Installationsbefehle vor,
- führt Paketinstallationen nur nach ausdrücklicher Zustimmung aus,
- kann eine bestehende Installation **wiederverwenden** oder mit Sicherung
  aktualisieren,
- überschreibt keine Laufzeitdaten, persönlichen Einstellungen oder
  vorhandenen Projektkonfigurationen,
- und installiert Programmdateien, Vorlagen, Startbefehl und die Registrierung
  vorhandener Git-Projekte aus dem Repository.

## Ausgangslage

- `install-vibe.sh` war ein Fedora-Container-Skript. Es verlangte `VIBE`, `tmux`
  und `flock`, kopierte Dateien fest nach `$VIBE/_toolchain`, überschrieb
  Vorlagen und beendete pauschal eine laufende `vibe-ui`-tmux-Sitzung.
- Es gab keine Plattformerkennung, keine Werkzeugdiagnose mit
  Installationsangebot, keine Windows-Unterstützung und keine Wahl zwischen
  Wiederverwendung und Aktualisierung.
- Die vorhandene Installation enthält bereits persönliche Laufzeitdaten
  (`vibe.json`, `models.json`, `profiles.json`, `fritz.json`, `_logs`). Ein
  Setup durfte diese nicht ersetzen.

## Fachliche Änderung

### Aufruf

```
python3 scripts/setup-vibe.py            # interaktiv
setup-vibe.cmd                           # Windows-Einstieg
VIBE=/pfad/zu/VibeCode bash install-vibe.sh   # kompatibel, ohne Rückfragen
```

Wichtige Optionen:

- `--vibe PFAD` Zielordner (sonst vorhandenes `VIBE`, sonst `~/VibeCode`).
- `--reuse` bestehende Installation nur ergänzen, nichts überschreiben.
- `--update` Programmdateien ersetzen und geänderte Dateien sichern.
- `--yes` ohne Rückfragen (Standard bei `install-vibe.sh`).
- `--install-deps` fehlende Werkzeuge ohne Rückfrage installieren.
- `--skip-deps` keine Werkzeuginstallation anbieten.
- `--dry-run` nur Plan anzeigen, nichts schreiben oder ausführen.
- `--no-register`, `--no-launcher` für gezielte Installationen.

### Plattformerkennung

| Umgebung | Erkennung | Paketweg |
| --- | --- | --- |
| Ubuntu/Debian | `/etc/os-release`, `ID`/`ID_LIKE` | `apt-get` |
| Fedora | `ID=fedora` oder `ID_LIKE=fedora` | `dnf` |
| Bazzite (Host) | `ID=bazzite` und `/run/ostree-booted` | kein Host-Layern; Hinweis auf Distrobox |
| Container | `/.dockerenv`, `/run/.containerenv`, `/run/.toolboxenv`, `container` | Paketmanager der Container-Distribution |
| Windows | `platform.system()` | `winget`; `tmux`/`flock` nur über WSL2/Docker |
| WSL | `WSL_DISTRO_NAME`/`WSL_INTEROP` oder `microsoft` in `/proc/version` | wie Linux |

### Werkzeuge

Geprüft werden `git`, `tmux`, `flock` (util-linux), `curl` und `opencode`.
Python wird auf `>= 3.8` geprüft. Fehlende Linux-Pakete werden zu **einer**
Argumentliste zusammengefasst (z. B. `sudo dnf install -y git tmux util-linux
curl`). `opencode` wird über `npm install -g opencode-ai` angeboten, wenn
`npm` vorhanden ist; andernfalls nennt der Setup die offizielle Adresse
`https://opencode.ai/docs/` und ruft kein Netzskript auf. Unter Windows
installiert `winget` Git; `tmux`/`flock` werden nicht vorgetäuscht, sondern als
WSL2-/Docker-Voraussetzung gemeldet.

Alle Befehle werden als Argumentlisten ohne Shell ausgeführt. Paketbefehle
laufen nur nach Zustimmung (oder mit `--install-deps`) und mit 30-Minuten-
Timeout.

### Wiederverwenden und Aktualisieren

- **Ohne bestehende Installation:** Modus `update`, alle Programmdateien,
  Vorlagen und der Modellkatalog werden kopiert.
- **Bestehende Installation, interaktiv:** Frage nach `w` (wiederverwenden),
  `a` (aktualisieren) oder `q` (abbrechen). Standard ist `w`.
- **Bestehende Installation, `--yes` ohne Modus:** `reuse` (sicher).
- **`reuse`:** kopiert nur fehlende Programm-/Vorlagendateien; vorhandene
  Dateien bleiben bytegleich.
- **`update`:** ersetzt geänderte Programm- und Vorlagendateien, sichert die
  vorherigen Fassungen unter `_toolchain/backup-<Zeitstempel>/...`.
  Unveränderte Dateien werden nicht kopiert und nicht gesichert.
- **Immer unangetastet:** `vibe.json`, `models.json`, `profiles.json`,
  `fritz.json`, `_logs`, `.vibe/project.env` und Projektdateien.

### Startbefehl und Projekte

- Linux: Symlink `~/.local/bin/vibe` auf `_toolchain/bin/vibe`; ein
  vorhandener Startbefehl wird als `vibe.bak-<Zeitstempel>` gesichert.
- Windows: `vibe.cmd` im Zielordner mit `py -3 "%~dp0_toolchain\bin\vibe" %*`.
- Vorhandene Git-Projekte (`.git` als Ordner oder Datei) erhalten nur dann
  eine `.vibe/project.env`, wenn sie fehlt. Android-Projekte mit `gradlew`
  bekommen die Android-Vorlage, sonst `generic`. Versteckte Ordner,
  `_toolchain` und Ordner ohne Git werden ignoriert.
- Es werden keine Projektbefehle, Builds oder Modellaufrufe ausgeführt.

## Technische Änderung

### `scripts/setup-vibe.py` (neu)

Reine Standardbibliothek; importierbar ohne Nebenwirkung. Zentrale Funktionen:

- `detect_platform(...)` — Betriebssystem, Distribution, Container, ostree,
  WSL, Paketmanager, `npm`-/`wsl`-Verfügbarkeit.
- `dependency_report(...)` — Präsenz, Installierbarkeit und Hinweis je
  Werkzeug.
- `privilege_prefix(...)` — `[]`, `["sudo"]` oder `None` (keine Rechte).
- `install_commands(...)` — Argumentlisten für apt/dnf/pacman/winget/npm.
- `validate_target(...)` — lehnt `/`, Systemordner, Home, Quellcodeordner und
  Ziele innerhalb des Quellcodes ab.
- `detect_existing(...)`, `install_program_files(...)`,
  `install_launcher(...)`, `register_projects(...)`,
  `verify_installation(...)`.
- `main(...)` — interaktiver bzw. nicht-interaktiver Ablauf mit injizierbaren
  Ein-/Ausgaben, `which`, Prozessläufer und Plattformdaten (testbar ohne echte
  Paketinstallation).

Dateikopien erfolgen über eine temporäre Datei im Zielordner und `os.replace`
(atomar innerhalb desselben Dateisystems). Sicherungen sind kollisionsfrei.
Auf FUSE/NTFS werden Ausführungsrechte nur best-effort gesetzt; es wird keine
wirksame Unix-Rechtegarantie behauptet.

### Nachbesserungen nach dem ersten Stand

- Der Bazzite-Hinweis nannte `bash scripts/setup-vibe.sh` — eine Datei, die es
  nicht gibt. Er verweist jetzt auf das vorhandene
  `python3 scripts/setup-vibe.py`; ein Test prüft, dass der Hinweis nur
  existierende Skriptpfade nennt.
- Der Windows-Startbefehl `vibe.cmd` wurde bei jedem Lauf erneut „geändert“,
  weil die Datei mit universellen Zeilenenden gelesen, aber mit CRLF
  geschrieben wird. Der Vergleich normalisiert jetzt die Zeilenenden; ein
  zweiter Lauf sichert und schreibt nichts mehr.
- `validate_target` löst jetzt Symlink-Ketten auf (`Path.resolve`) und prüft
  sowohl den angegebenen als auch den aufgelösten Pfad gegen die abgelehnten
  Ziele. Ein Symlink auf `/usr` oder in den Quellcodeordner wird damit
  abgewiesen; ein Test deckt diesen Fall ab.
- Fehlerpfade der Werkzeuginstallation sind jetzt getestet: Rückgabecode
  ungleich 0, fehlender Paketmanager nach Zustimmung (`OSError`) und
  Zeitüberschreitung (`subprocess.TimeoutExpired`). Der Setup meldet diese
  Fälle sichtbar und bricht mit Code 2 ab.

### `install-vibe.sh`

Delegiert jetzt an `scripts/setup-vibe.py --yes --update --vibe "$VIBE"` und
behält die `VIBE`-Pflicht. Das frühere pauschale Beenden von `vibe-ui` entfällt:
Ein laufendes Dashboard wird nicht mehr unterbrochen und nutzt den neuen Stand
erst beim nächsten Start. Diese Änderung ist bewusst, weil ein Installer keine
laufenden Prozesse beenden soll.

### `setup-vibe.cmd` (neu)

Windows-Einstieg: prüft `py`, installiert bei Bedarf Python über
`winget install --id Python.Python.3.12 -e` und startet
`py -3 "%~dp0scripts\setup-vibe.py" %*`.

## Entscheidungen und Begründungen

- **Python statt Bash:** Python ist auf Linux, in Containern und unter Windows
  vorhanden bzw. über `winget` installierbar; ein Bash-Skript wäre unter
  Windows nativ nicht lauffähig. Es bleibt bei der Standardbibliothek.
- **Kein automatisches `curl | bash`:** Ein remotely gepipetes Skript wäre
  weder testbar noch sicher. `opencode` wird über npm oder die offizielle
  Installationsseite angeboten.
- **Zustimmung statt stiller Systemänderung:** Paketinstallationen sind
  sichtbar, einzeln bestätigt und als Argumentliste ausgeführt. `--yes`
  installiert ohne `--install-deps` keine Systempakete.
- **`reuse` als sicherer Standard:** Eine bestehende Installation wird nicht
  versehentlich überschrieben. `install-vibe.sh` fordert für den bisherigen
  Update-Charakter ausdrücklich `--update` an.
- **Laufzeitdaten getrennt:** `_toolchain` enthält Programm und Laufzeitdaten.
  Nur Programmdateien und fehlende Vorlagen werden kopiert; Konfigurationen
  und Logs bleiben unangetastet.
- **Windows ohne falsches Versprechen:** Dateien und Oberfläche lassen sich
  installieren; Agentenläufe brauchen `tmux`/`flock`. Statt einer Attrappe wird
  WSL2/Docker als Voraussetzung genannt.
- **Bazzite nicht layern:** Auf unveränderlichen Systemen wäre `rpm-ostree`
  mit Neustart verbunden; der Setup verweist auf den vorhandenen
  Distrobox-/Containerweg.

## Grenzen

- **Windows wurde nicht real ausgeführt.** Die Plattformlogik, der
  `.cmd`-Inhalt und der `winget`-Befehl sind statisch bzw. mit simulierten
  Daten geprüft. Ein echter Windows-/WSL-Lauf steht aus.
- **Kein realer Paketmanager-Lauf** in den Tests. Die Befehlsbildung,
  Zustimmung, Argumentlisten und Fehlerbehandlung sind mit einem injizierten
  Läufer geprüft; ein echter `apt-get`/`dnf`/`pacman`/`winget`-Lauf wurde nicht
  ausgeführt.
- **Bazzite-Host** wird nur erkannt und beraten; es wird nichts auf dem Host
  geschichtet.
- **npm-Version:** Der Setup installiert das npm-Paket `opencode-ai`, geprüft
  über `npm view opencode-ai name`. Ob die damit installierte CLI-Version zur
  jeweils gewünschten opencode-Funktion passt, bleibt Gegenstand von V-007.
- **Keine vollständige V-018-Semantik:** Es gibt Sicherungen und
  Wiederverwendung, aber noch keine Versionskennung, kein transaktionales
  Update und keinen automatisierten Rollback.
- **FUSE/NTFS:** Atomare Ersetzung und Ausführungsrechte hängen vom
  Dateisystem ab; es werden keine wirksamen Unix-Rechte garantiert.
- **Android/Java/Emulator** sind projektspezifische Werkzeuge und werden nicht
  global installiert (SPEC: keine globale Android-Voraussetzung).
