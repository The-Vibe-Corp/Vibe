# V-014 — MCP-Verbindungstests robust und begrenzt ausführen

Stand: 2026-10-30
Ausgangscommit: `9680cb8`
Arbeitsbranch: `feature/v-014-mcp-tests`

## Ziel

Die MCP-Verwaltung konnte Server anzeigen, bearbeiten und testen. Der Test
öffnete jedoch ein lokales Programm ohne eigene Prozessgruppe, las
Serverausgaben und HTTP-Antworten unbegrenzt und unterschied Fehler nur über
freie Texte. Ein Dauerstream konnte den Test blockieren, gestartete
Kindprozesse liefen weiter, und OAuth-Grenzen sowie der tatsächlich geprüfte
Transport waren nicht sichtbar.

Dieses Arbeitspaket macht den Verbindungstest begrenzt, aufräumbar und
diagnostisch eindeutig. Er prüft weiterhin nur den Handshake und die
Werkzeugliste; fachliche Werkzeuge werden nicht aufgerufen.

## Lieferumfang

- `bin/vibe_mcp.py` — Handshake mit Transportauskunft, Startwarnung,
  Fehlerkategorien, OAuth-Hinweis, Limits, Prozessgruppen-Cleanup und
  Geheimnismaskierung der Diagnose.
- `bin/vibe-web.py` — sichtbare Startwarnung, Transport- und Fehlerart in der
  Ergebnisanzeige, Hinweise ohne Häkchenkennzeichnung.
- `tests/unit/test_mcp_test.py` — 18 Tests mit lokalen Mockservern,

  Kindprozess, Timeout und unbekanntem Transport.
- `docs/compatibility.md` — transport-, limit- und fehlerbezogene
  Kompatibilitätsaussagen.
- `docs/import-manifest.json` — aktualisierte Prüfsummen und Eintrag `V-014`.
- `docs/features/V-014.md` — diese Dokumentation.

## Fachliche Umsetzung

### Ablauf und Grenzen

Der Test führt genau diese Schritte aus:

1. `initialize` senden und Serveridentität lesen.
2. `notifications/initialized` senden (bei `remote` ohne Auswertung der
   Antwort).
3. `tools/list` senden und die Werkzeugliste anzeigen.

Ein `tools/call` wird nie automatisch gesendet. Die Oberfläche und die CLI
nennen das vor dem Test; das Ergebnis enthält denselben Hinweis.

### Unterstützte Transporte

| Typ | Anzeige | Vorgehen |
| --- | --- | --- |
| `local` | local – Standard-Ein-/Ausgabe (stdio) | Programm aus `command` mit Argumentliste starten, JSON-RPC je Zeile |
| `remote` | remote – Streamable HTTP (JSON oder Server-Sent Events) | POST mit `Accept: application/json, text/event-stream` |

Ein unbekannter `type` oder ein URL-Schema außer `http://`/`https://` wird als
`unsupported_transport` gemeldet. Die Meldung nennt die unterstützten
Transporte und stellt klar, dass dies kein Hinweis auf einen defekten Server
ist. Klassische SSE-Endpunkte (`GET /sse`) werden nicht getestet.

### Startwarnung

Vor dem Test wird erklärt, dass `local` ein Programm startet und `remote`
eine Netzverbindung herstellt und dass dies nicht garantiert
nebenwirkungsfrei ist. Die Warnung steht in der Oberfläche, in der CLI und im
Ergebnisobjekt (`warning`).

### OAuth-Grenzen

vibe führt keine OAuth-Anmeldung durch, öffnet keinen Browser und liest keine
Tokens. Bei konfiguriertem OAuth weist das Ergebnis darauf hin, dass zuerst
`opencode mcp auth <name>` ausgeführt werden muss. Ein HTTP-401/403 wird als
`auth` gemeldet und getrennt von Protokoll- oder Netzfehlern behandelt.

### Fehlerarten

| Kategorie | Bedeutung |
| --- | --- |
| `program` | Programm fehlt oder startet nicht |
| `timeout` | Zeitlimit ohne Antwort |
| `dns` | Name nicht auflösbar |
| `tls` | TLS-/Zertifikatsfehler |
| `network` | Verbindung nicht möglich |
| `http` | anderer HTTP-Fehler |
| `auth` | HTTP 401/403, Anmeldung nötig |
| `protocol` | ungültige oder unerwartete MCP-Antwort |
| `config` | ungültige Konfiguration; es wird nichts gestartet |
| `unsupported_transport` | Transport wird nicht unterstützt |

Nach dem Handshake unterscheidet `local` genauer: Endet der Prozess ohne
Antwort auf `tools/list`, ist das `protocol`; läuft er weiter, ist es
`timeout`. Eine erreichte Ausgabegrenze wird zusätzlich genannt.

### Limits

- Wartezeit: mindestens 5 s, höchstens 90 s (`local`) beziehungsweise 60 s
  (`remote`); das konfigurierte `timeout` wird darauf begrenzt. Bei `remote`
  gilt die Frist je Anfrage einschließlich des Wartens auf Status und Header;
  die `initialized`-Benachrichtigung hat zusätzlich höchstens 5 s.
- Werkzeugliste: 200 Einträge, Name 120 Zeichen, Beschreibung 160 Zeichen.
- Stdio: 4 MiB stdout; stderr wird ab 4000 Zeichen gekürzt, aber weiter
  gelesen, damit der Server nicht blockiert.
- HTTP: 1 MiB Antwort; ein Server-Sent-Events-Stream endet nach der gesuchten
  Antwort oder am Zeitlimit.
- Diagnose: Fehler 1000 Zeichen, Hinweis 2000 Zeichen, höchstens 40 Schritte.

### Prozesscleanup

`local`-Prozesse starten in einer eigenen Sitzung (`start_new_session`). Nach
Erfolg, Fehler oder Timeout wird die gesamte Prozessgruppe mit `SIGKILL`
beendet und der Prozess abgewartet; anschließend werden stdin, stdout und
stderr geschlossen. Dadurch enden auch Kindprozesse eines Mockservers. Auf
Systemen ohne POSIX-Prozessgruppen wird der Prozess direkt beendet.

### Geheimnisse

Vor der Ausgabe werden konkrete Geheimwerte aus `environment`, geheimen
Headern, geheimen URL-Parametern, `oauth.clientSecret` und geheimen Argumenten
durch `***` ersetzt. Zusätzlich maskiert die Ausgabe `Bearer`-/`Basic`-Werte
und Zuweisungen wie `token=…`. Die Maskierung greift auch für
Serverausgaben, Fehlertexte, Schritte und Serverangaben.

Nicht erkennbar sind Geheimnisse, die als unbenanntes positionales Argument in
`command` stehen (z. B. `["server", "geheim"]`), weil sie nicht von normalen
Argumenten unterscheidbar sind. Geheime Werte gehören deshalb in
`environment`, in geheime Header, in benannte Optionen wie `--token` oder in
URL-Parameter.

## Technische Umsetzung

`vibe_mcp._result()` erzeugt das gemeinsame Ergebnis mit `transport`,
`warning`, `notes`, `limits` und `supported_transports`. `_fail()` setzt die
Kategorie, `_finish()` maskiert Geheimnisse und begrenzt die Textlängen.

`test_local()` liest stdout und stderr in getrennten Threads. stdout wird bis
4 MiB in eine Queue gestellt, darüber hinaus verworfen, aber weiter gelesen.
Wird das Limit erreicht, nennt das Ergebnis die verworfene Ausgabe auch dann,
wenn der Handshake ausbleibt. stderr wird auf 4000 Zeichen gekürzt und weiter
drainiert. `wait()` prüft das Zeitlimit und erkennt einen beendeten Prozess.
`_close_process()` beendet die gesamte Prozessgruppe.

`test_remote()` liest HTTP-Antworten über `_read_http()`. Bei
`text/event-stream` wird zeilenweise gelesen und nach der Antwort mit der
gesuchten ID abgebrochen; sonst wird die Antwort bis 1 MiB gelesen. Beide
Pfade prüfen eine absolute Frist. `HTTPError` wird geschlossen und die
Fehlerantwort gekürzt übernommen.

`test()` prüft zuerst den Transport, dann die Konfiguration. Ein unbekannter
Transport oder ein ungültiger Eintrag liefert ein Ergebnis statt einer
Ausnahme, damit die Oberfläche eine Diagnose anzeigen kann.

`_payload()` akzeptiert eine JSON-RPC-Antwort nur dann als Ergebnis, wenn
`result` ein Objekt ist. Fehlt es oder hat es einen anderen Typ, melden beide
Transporte `protocol` mit einer verständlichen Meldung, statt mit einer
Ausnahme abzubrechen. `_server_info()` reicht `serverInfo` nur als Objekt
weiter, damit die Oberfläche keine unerwarteten Typen erhält.

## Tests

`tests/unit/test_mcp_test.py` enthält 18 Tests:

- lokaler Handshake mit aufgezeichneten Methoden (kein `tools/call`),
- große Ausgabe und auf 200 begrenzte Werkzeugliste,
- Ausgabe über 4 MiB wird verworfen und als Ausgabelimit gemeldet,
- Kindprozess wird mitbeendet,
- Timeout mit Kategorie `timeout`,
- keine Antwort auf `tools/list` ergibt `timeout` statt `protocol`,
- Geheimnis aus `environment` erscheint nicht im Ergebnis,
- `initialize` mit `result: null` ergibt `protocol` statt einer Ausnahme,
- unerwartete `serverInfo` wird nicht ungeprüft durchgereicht,
- HTTP-Handshake mit Sitzungskennung und aufgezeichneten Methoden,
- Authfehler mit OAuth-Hinweis und ohne Header-Geheimnis,
- Protokollfehler,
- `tools/list` mit `result: null` ergibt `protocol` statt einer Ausnahme,
- Dauerstream endet nach der Antwort,
- OAuth wird nicht ausgeführt und ist sichtbar,
- unbekannter `type`,
- unbekanntes URL-Schema (WebSocket),
- ungültige Konfiguration.

Alle Server sind lokale Attrappen; es werden keine echten MCP-Server,
opencode-Dienste oder Modellanbieter aufgerufen.

## Nachweise

- `bash scripts/verify.sh quick` → Exit 0: 31 Manifestdateien, 59 Python-,
  6 Bash- und 4 JSON-Dateien syntaktisch geprüft, keine Geheimnisse.
- `bash scripts/verify.sh full` → Exit 0: 604 Unit- und 47 Browsertests
  (`Ran 604 tests … OK`, `Ran 47 tests … OK`), 651 Tests erkannt,
  Prüfverzeichnis wieder entfernt.
- Detailtests: `python3 -m unittest tests.unit.test_mcp_test -v` → 18 Tests OK.

Der `full`-Lauf wurde in einer privaten Mount-Namespace mit beschreibbarem
`/tmp` (`bwrap --dev-bind / / --tmpfs /tmp`) und ohne die Harness-Variablen
`SANDBOX`/`SANDBOX_TOOLS` ausgeführt, weil die Testumgebung des Hosts `/tmp`
schreibgeschützt einbindet und die Sandbox-Tests feste Pfade unter `/tmp`
verwenden. Die Tests selbst wurden dabei nicht verändert; die Abweichung
betrifft nur die Ausführungsumgebung. Ohne diese Trennung schlagen die
Läufer-, Fritz- und Sandbox-Tests unabhängig von diesem Arbeitspaket fehl.

## Grenzen

- Der Test beweist nur, dass der Server den Handshake und die Werkzeugliste
  beantwortet. Er beweist nicht, dass ein Agent die Werkzeuge nutzen darf.
- Klassische SSE-Transporte und WebSockets werden nicht getestet.
- OAuth wird nicht ausgeführt; ohne vorherige Anmeldung kann ein Test mit
  HTTP 401 enden.
- Die Zeit- und Ausgabelimits sind fest im Code hinterlegt und nicht je
  Projekt konfigurierbar.
- Die Tests verwenden Attrappen. Ein echter Server eines Anbieters wurde in
  diesem Arbeitspaket nicht aufgerufen.
