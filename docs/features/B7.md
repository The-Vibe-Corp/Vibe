# B7 — GitHub-Authentifizierung über die Oberfläche (Bug zu AP6)

Stand: 2026-11-10
Art: Bug
Arbeitsbranch: `vibe/vibe-B7-1794295794403437735-1660139-21935`

## Symptom

„Fast alle Knöpfe in den GitHub-Einstellungen funktionieren nicht.“ Die
Meldungen kamen zu spät (innerhalb des Ablauf-Timeouts) und verschwanden
zu schnell, um sie zu erfassen. Die Ausgaben lauteten:

- `cannot exec '/usr/bin/ksshaskpass': Datei oder Verzeichnis nicht gefunden`
- `could not read Username for 'https://github.com': terminal prompts disabled`

Der Nutzer erhielt zu keiner Zeit eine Abfrage, Anweisung oder Erklärung
zur Authentifizierung.

## Ursache

1. **Kein Auth-Weg:** AP6 las den Token ausschließlich aus der Umgebung
   (`GITHUB_TOKEN`/`GH_TOKEN`). Weder die Karte „Git & GitHub“ noch die
   CLI boten eine Anleitung oder ein Eingabefeld. Git-Aktionen gegen
   `https://github.com` liefen daher ohne Zugangsdaten auf den
   (hier kaputten, weil unvollst. installierten) askpass-Weg und
   endeten bei deaktivierten Terminal-Prompts mit den genannten Fehlern.
2. **Issues ohne Token:** `vibe github <p> issues`/`issues-import`
   übergeben an `list_issues` überhaupt keinen Token — selbst mit
   Umgebungstoken liefen diese Abfragen unauthentifiziert.
3. **Fehler zu kurz:** fehlgeschlagene Karten-Aktionen (Abrufen, Pull,
   Push) erschienen nur als Toast (8 Sekunden, automatisch verschwunden)
   und nicht in der dauerhaften Fehlerbox der Karte; die Card-Codepfade
   riefen `setErr` erst gar nicht.

## Änderung

### Token-Speicher (`bin/vibe_github.py`)

- `token_state_path()`/`save_token()`/`read_stored_token()`/`delete_token()`:
  Der Token wird im Zustandsordner (`VIBE_STATE`) gespeichert —
  ausdrücklich **außerhalb jedes Git-Repositorys** (SPEC: Geheimnisse
  werden nicht ins Repository aufgenommen). Implementierung über
  temporäre Datei + `os.replace`; Modus 0600 **best effort** (auf
  FUSE/NTFS wird kein falsches Sicherheitsversprechen gemacht).
  Ungültige Eingaben (leer, Steuerzeichen) werden vor dem Schreiben
  abgelehnt und hinterlassen keine Reste.
- `token_status()` meldet `{"set": bool, "source": "umgebung"|"gespeichert"|""}`
  ohne Inhalte; Quelle **umgebung** gewinnt (`GITHUB_TOKEN`/`GH_TOKEN`).

### Zugangsdaten-Ausdeckung

- `git()` löst die Zugangsdaten auf (umgebungstoken ODER gespeicherte
  Datei) und legt sie **nur für github.com** an: URL-gültige
  Konfiguration `credential.https://github.com.helper` über die
  `GIT_CONFIG_*`-Umgebungskonfiguration — nicht über argv, nicht über
  die Konfigurationsdateien. Der Tokeninhalt liegt ausschließlich in der
  Prozessumgebung (`VIBE_GITHUB_CREDENTIAL`).
  - Credential-Schema: `x-access-token` als Benutzername, Token als Kennwort
  — die GitHub-Konvention für App-/Fine-grained-Tokens.
- Gespeicherte Zugangsdaten werden **niemals** an andere Hosts gesendet
  (REST nur für die offizielle `https://api.github.com`, Git nur für
  github.com-URLs). Umgebungstoken behalten das bisherige REST-Schema.
- Ohne Token bleibt das Git-Verhalten unverändert
  (`GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`).

### Fehlerklassifikation

Karten-/CLI-Meldungen, die ein Auth-Bild enthalten, (`could not read Username`,
`terminal prompts disabled`, `Authentication failed`, `cannot exec`,
`askpass`) erhalten einen klaren Anweisungssatz (Token in der Karte
hinterlegen oder `GITHUB_TOKEN` setzen; GitHub-Empfehlung:
Personal Access Token). Geheimnisse erscheinen auch weiter nie.

`list_issues` und `create_pull_request` lösen einen Token ohne ausdrückliche Angabe automatisch über `token_for_rest(api)` auf: Umgebungstoken, sonst gespeicherter
Token (nur für die offizielle API). Fehlschlag ohne Token bleibt
verständlich („Kein GitHub-Zugangstoken …“).

### Web-API (`bin/vibe-web.py`, `/api/github`)

- `token.save` speichert (`body.token`, niemals in der Antwort), 
- `token.clear` entfernt.
- Der GitHub-Status in der Antwort trägt zusätzlich `auth`
  (`{"set","source"}`) ohne Geheimnis; die V-004-Regeln (Token-Pflicht,
  Limits, Geheimnisfreihaltung) gelten weiter.

### Projektansicht / Karte (`bin/web/app.js`, `bin/vibe_services.py`)

- Auth-Block oben in der Karte (immer sichtbar, auch ohne aktivierte
  Verknüpfung): Statuszeile („Kein Token hinterlegt — für Push, private
  Repositories und Merge-Requests ist ein Token nötig…“, bei Zustand die
  Quelle), Token-Eingabe als Passwortfeld, Aktionen „Token hinterlegen“
  und „Token entfernen“. Nach Erfolg wird die Statuszeile **direkt in
  der Zeile** aktualisiert (kein Refresh), damit der aufklappbare
  AP7-Abschnitt offen bleibt.
- Fehlgeschlagene Aktionen (Abrufen, Pull, Push, Merge-Request, Issues,
  Import) schreiben ihre Meldung zusätzlich in die dauerhafte
  Karten-Fehlerbox; sie bleibt bis zur nächsten Aktion oder zum nächsten
  Erfolg stehen — der kurzlebige Toast bleibt daneben erhalten.
- Der degradierte GitHub-Fallback der Projektansicht liefert ebenfalls
  `auth`.

### CLI (`bin/vibe github`)

- `vibe github <projekt> token` hinterlegt den Token (Eingabe unsichtbar
  per getpass, nie als Argument (kein Argv-Leak));
  `vibe github <projekt> token clear` entfernt ihn.
- `status` zeigt die Quelle des Zugangstoken ohne Inhalt.

## Entscheidungen (dokumentiert)

- **Globale Speicherung im Zustandsordner anstatt je Projekt:** Ein
  GitHub-Zugang gehört in dieser Installation zum Nutzer, nicht zum
  Projekt (GitHub empfiehlt einen Personal Access Token über HTTPS,
  nur für die jeweils benötigten Repos freigegeben). Die AP6-Konfiguration
  (Enabled/Repo/Label/API) bleibt je Projekt. Ein per Projekt
  abweichender Token ist bisher nicht erforderlich und war Offenlassung.
- **Übertragungsweg:** Die aktuelle GitHub-Empfehlung für Git über HTTPS
  ist das PAT statt Kennwörtern (Kennwort-Authentifizierung ist dort
  abgeschaltet).
  Der generische Benutzername `x-access-token` mit Token als Kennwort ist
  die GitHub-Konvention (GitHub-App-/Fine-grained-Schema, faktisch auch
  für klassische PATs akzeptiert); für Sonderfälle bleibt ein
  Umgebungstoken über `GITHUB_TOKEN` jederzeit die Rückfallebene.

## Grenzen

- AP6-Regeln unverändert: kein automatischer Push/Merge; jede
  Netzaktion bleibt eine bewusste Nutzeraktion.
- SSH-Remotes (`git@github.com:…`) nutzen nach wie vor SSH-Schlüssel des
  Nutzers; der Token-Weg betrifft HTTPS-Zugänge.
- Für GitHub Enterprise / andere Hosts gilt: Umgebungstoken über
  `GITHUB_TOKEN` an der konfigurierten API; der hinterlegte Token wird
  bewusst nicht an beliebige Hosts gesendet.
- Der Branchwechsel bleibt Leseansicht (AP6-Abgrenzung, Läufer arbeitet
  in eigenen Worktrees).
