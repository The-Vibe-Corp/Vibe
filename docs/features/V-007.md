# V-007 — opencode-Kompatibilitätsadapter

Stand: 2026-10-30
Ausgangscommit: `25bcc6a`
Arbeitsbranch: `feature/v-007-opencode-adapter`
Geprüfte opencode-Version: **2.1.4**

## Ziel

vibe verteilte Annahmen über opencode über CLI, MCP-Verwaltung und
Serverstart. Besonders kritisch war die MCP-Verwaltung: Sie leitete das
Konfigurationsschema allein aus der Hauptversionsnummer ab und nahm bei einer
leeren Datei `mcp.servers` an, ohne die installierte Version zu prüfen.

Dieses Paket kapselt Version, Modelllisting, Agentenregeln, MCP-Schema und
Serverstart in einem Adapter. Unbekannte Versionen werden gemeldet und
versionabhängige Schreibvorgänge abgelehnt, statt sie wie die geprüfte Version
zu behandeln.

## Lieferumfang

- `bin/vibe_opencode.py` — neuer Adapter (Standardbibliothek, importfrei):
  Versionsprüfung, geprüftes Profil 2.1.4, Modelllisting, Agentenregeln,
  MCP-Schemaerkennung und Serverbefehl.
- `bin/vibe` — Modelllisting, Agentenvalidierung, Projekt-Agentenverzeichnis,
  Serverstart und Doctor-Ausgabe nutzen den Adapter. Der Serverstart verwendet
  `opencode serve` statt des ungeprüften `opencode web`.
- `bin/vibe_mcp.py` — Schemaerkennung über den Adapter; Schreibvorgänge werden
  bei unbekanntem Schema abgelehnt. Die Annahme „Hauptversion ≥ 2 bedeutet
  `mcp.servers`“ ist entfernt.
- `scripts/setup-vibe.py` — der neue Adapter wird mitinstalliert.
- `docs/compatibility.md` — geprüfte Version, Prüfverfahren, Schemabeleg,
  Verhalten bei unbekannten Versionen und Grenzen.
- `tests/unit/test_opencode_adapter.py` — 39 Tests mit Fixtures und Attrappen.
- `tests/unit/test_setup_vibe.py` — Installationsliste um den Adapter ergänzt.
- `docs/import-manifest.json` — Prüfsummen der geänderten Dateien und Eintrag
  `V-007` unter `aenderungen`.

## Technische Umsetzung

### Versionsprüfung

`probe()` startet `opencode --version` mit einer Argumentliste und ohne Shell.
Die Ausgabe wird mit `v?X.Y.Z` gelesen. Statuswerte:

| Status | Bedeutung | Verhalten |
| --- | --- | --- |
| `supported` | exakt `2.1.4` | Profil wird verwendet |
| `unknown` | lesbar, aber nicht geprüft; oder Ausgabe nicht lesbar | Warnung; versionabhängige Schreibvorgänge abgelehnt |
| `missing` | Exit 127 | verständliche Meldung |
| `timeout` | Exit 124 | verständliche Meldung |
| `error` | anderer Exitcode | Exitcode und Ausgabe in der Meldung |

`require_supported()` nennt in der Fehlermeldung immer die geprüfte Version
`2.1.4`. `vibe doctor` zeigt die erkannte Version als eigene Prüfzeile.

### Modelllisting

`list_models()` verwendet für die geprüfte Version
`opencode models --standalone`. Der private Server vermeidet eine Kollision mit
einem bereits laufenden verwalteten opencode-Dienst. Gelesen werden nur Zeilen
im Format `anbieter/modell`.

Fehlerfälle werden getrennt behandelt:

- Exit 127: Programm fehlt.
- Exit 124: Zeitüberschreitung.
- anderer Exit: Fehlercode und gekürzte Ausgabe.
- Exit 0 mit nicht erkennbarer Ausgabe: Fehler, keine leere Erfolgsliste.
- Exit 0 ohne Ausgabe: gültige leere Liste.
- ungeprüfte, aber lesbare Version: Liste mit Warnung.

### Agenten

`agent_directory()` liefert `<projekt>/.opencode/agents`.
`validate_agent()` prüft die Regeln der geprüften Version: Pflichtfeld
`description`, erlaubte Modi `primary`, `subagent`, `all` und einen nichtleeren
Prompt. `vibe.agent_validate()` ergänzt nur noch die vibe-spezifische
Platzhalterprüfung.

### MCP-Schema

`detect_mcp_layout()` prüft zuerst die tatsächliche Konfiguration:

1. `mcp.servers` ist ein Objekt → `servers`.
2. Serverobjekte direkt unter `mcp` → `classic`.
3. Nicht zuordenbare Einträge unter `mcp` → `unknown`.
4. Leere Konfiguration und geprüfte Version → geprüftes Profil (`servers`).
5. Leere Konfiguration und ungeprüfte Version → `unknown`.

`vibe_mcp.save()`, `delete()` und `toggle()` lehnen `unknown` mit einer
Meldung ab, die die geprüfte Version nennt. Vorhandene Konfigurationen mit
eindeutigem Schema bleiben lesbar, auch wenn die Version ungeprüft ist.

### Serverstart

`server_command()` baut für 2.1.4:

```
opencode serve --hostname 127.0.0.1 --port <port>
```

Der tmux-Aufruf erhält diese Liste über `shlex.join`. Bei unbekannter Version
oder fehlendem Programm bricht `vibe server start` mit der Adaptermeldung ab,
ohne einen Prozess zu starten.

## Geprüfte Version und Verfahren

Die Version wurde in dieser Umgebung tatsächlich abgefragt:

```
$ opencode --version
opencode v2.1.4
```

Zusätzlich geprüft:

```
$ opencode models --standalone
modal-coder/coder
modal-review/reviewer
opencode/beam-free
...
$ echo $?
0
```

```
$ opencode serve --help
...
  --hostname string
  --port integer
...
```

Das MCP-Schema wurde in einem temporären Projekt mit einer isolierten
HOME-/Konfigurationsumgebung geprüft:

```
$ opencode mcp add probe -- echo hi
MCP server "probe" added to <temporäres Projekt>/opencode.json
```

Die geschriebene Datei enthielt `mcp.servers`. Einzelheiten und das Verfahren
für neue Versionen stehen in `docs/compatibility.md`.

## Tests

`tests/unit/test_opencode_adapter.py` deckt ab:

- Fixture der unterstützten Version 2.1.4 (auch mit Banner/Build-Suffix),
- unbekannte Version, unlesbare Ausgabe, fehlendes Binary, Fehlercode,
  Zeitüberschreitung (auch mit echtem Prozess),
- Modelllisting: gültige Ausgabe, leere Ausgabe, unerwartete Ausgabe,
  Fehlercode, fehlendes Binary, Timeout, Warnung bei ungeprüfter Version,
- Serverbefehl: geprüfte Argumentliste, Ablehnung unbekannter Version und
  fehlenden Programms, ungültiger Port,
- Agentenregeln: Verzeichnis, Pflichtfeld, Modus, leerer Prompt,
- MCP-Schema: `servers`, `classic`, gemischter Block (abgelehnt), leere
  Datei mit geprüfter/ungeprüfter Version, unbekannte Struktur,
- Integration: `vibe_mcp` liest `classic` ohne `servers`-Annahme, schreibt mit
  geprüfter Version `mcp.servers` und verweigert Schreiben bei ungeprüfter
  Version; `vibe.models_list`, `vibe.agent_validate`, `vibe.cmd_server` und
  `vibe.doctor_checks` nutzen den Adapter.

## Grenzen

- Geprüft ist ausschließlich opencode 2.1.4; andere Versionen werden bewusst
  nicht als kompatibel behandelt.
- `opencode debug agents` war in dieser Sitzung wegen eines belegten
  verwalteten Dienstports nicht nutzbar. Agenten werden deshalb aus den
  opencode-Markdown-Dateien gelesen; die Regeln liegen im Adapter.
- Die Modellliste ist keine Nutzungsberechtigung und keine Kostenaussage.
- Die Tests verwenden Attrappen und Fixtures; sie ersetzen keine manuelle
  Prüfung einer neu installierten opencode-Version.
