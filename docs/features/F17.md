# F17 — Agentenverwaltung je Projekt

Stand: 2026-11-02
Ausgangscommit: `0031166`
Arbeitsbranch: `feature/v-016-lebenszyklus`
Arbeitspaket: FEEDBACK.md, Eintrag F17

## Ziel

Zwei Änderungen an der Agentenverwaltung:

1. **Fehler behoben:** Eine im strukturierten Editor geänderte Modellauswahl
   wurde bisher nur gespeichert, wenn der Nutzer zusätzlich „In Rohtext
   übernehmen“ anklickte. Ein direkter Klick auf „Speichern“ verwarf die
   Änderung, weil nur der Rohtext gesendet wurde. Das betraf die allgemeine
   Agentenübersicht und jeden Agenten, nicht nur Modelle.
2. **Agenten je Projekt:** Jedes Projekt erhält im Projektdetail eine eigene
   Ansicht seiner Agenten. Der Nutzer wählt aus, welche Agenten in diesem
   Projekt eingesetzt werden, und kann je Agent das Modell überschreiben.
   Standard ist die übergreifende Konfiguration. Ein abgewählter Agent wird
   beim Agentenlauf abgelehnt; eine Modellüberschreibung wird an
   `opencode run --model` weitergereicht.

## Ausgangslage

Die Agentenverwaltung (V-010) kannte globale Agenten und Projektagenten in
`.opencode/agents`. Auswahl und Modell je Projekt waren nicht vorhanden. Der
strukturierte Editor und der Rohtext-Editor waren getrennte Wege: Änderungen
in den Formularfeldern landeten erst nach einem zusätzlichen Klick im Rohtext,
und nur der Rohtext wurde gespeichert.

## Fachliches Verhalten

### Modellauswahl speichern (Fehlerbehebung)

- „Speichern“ übernimmt geänderte strukturierte Felder unmittelbar, ohne
  „In Rohtext übernehmen“. Das gilt für Modell, Beschreibung, Modus,
  Temperatur, Schritte, Rechte und Prompt.
- Es werden nur Felder gesendet, die sich seit dem Laden des Agenten geändert
  haben. Freie Änderungen am Rohtext an anderen Stellen bleiben dadurch
  erhalten; der Rohtext bleibt für bekannte Felder maßgeblich, solange das
  Formularfeld nicht geändert wurde.
- Ungültige strukturierte Werte werden vor jedem Schreiben abgelehnt; die
  Datei bleibt unverändert.
- Agenten mit defektem Frontmatter werden weiterhin nur im Rohtext bearbeitet.

### Agentenauswahl je Projekt

- Ohne eigene Projektdatei sind alle verfügbaren Agenten ausgewählt. Das Modell
  kommt aus der jeweiligen Agentendatei.
- Ein Projektagent überschreibt einen gleichnamigen globalen Agenten und wird
  in der Liste nur einmal geführt (opencode-Priorität).
- Ein abgewählter Agent bleibt für andere Projekte unverändert ausgewählt und
  ist nur im gewählten Projekt gesperrt.
- Ein Modell kann je Projekt und Agent überschrieben werden. Eine leere Auswahl
  entfernt die Überschreibung; dann gilt wieder das Modell aus der
  Agentendatei.
- Ein Agent eines anderen Projekts kann nicht für dieses Projekt ausgewählt
  werden.
- `vibe project-agents <projekt>` zeigt Auswahl, Geltung, wirksames Modell und
  Überschreibung.
- Der Agentenlauf prüft die Auswahl vor dem Start: Ein abgewählter Agent führt
  zu einer verständlichen Meldung und es wird kein Lauf gestartet.

### Oberfläche

- Im Projektdetail, Reiter „Einstellungen“, zeigt die Karte „Agenten in diesem
  Projekt“ je Agent ein Kontrollkästchen und eine Modellauswahl.
- Die Tabelle nennt Geltung (global/Projekt) und das wirksame Modell.
- Jede Änderung wird sofort gespeichert und nach dem Neuladen erneut angezeigt.
- Ein fehlender Fehlerhinweis erscheint nicht als Text „null“ unter der Tabelle.
- Ein abgewählter Agent startet nicht; die Oberfläche erklärt das neben der
  Tabelle.

## Technische Umsetzung

### Speicher (`<projekt>/.vibe/agents.json`)

```json
{"version": 1, "deaktiviert": ["tester"], "modelle": {"tester": "opencode/modell"}}
```

- Gespeichert werden nur Abweichungen vom Standard. Eine fehlende Datei bedeutet
  „alle Agenten ausgewählt, Modell aus der Agentendatei“. Neue Agenten sind
  dadurch ohne Pflege aktiv.
- Geschrieben wird atomar über `vibe_storage.write_text`; bei einer gleichzeitigen
  Änderung wird mit `ConcurrentChangeError` abgebrochen (HTTP 409).
- Unbekannte Felder, falsche Typen, ungültige Agentennamen und Modellwerte mit
  Leerzeichen werden abgelehnt. Eine unlesbare Datei wird gemeldet und nicht
  stillschweigend überschrieben.
- `selected` muss ein JSON-Wahrheitswert sein; Zeichenketten wie `"nein"`
  werden abgelehnt, damit eine Abwahl nicht versehentlich als Auswahl gilt.
- Modellwerte werden auf `^[A-Za-z0-9][A-Za-z0-9._:/@+-]*$` geprüft.

### CLI (`bin/vibe`)

- `project_agent_inventory(project)` sammelt globale und projektspezifische
  Agenten; gleiche Namen werden durch den Projektagenten ersetzt.
- `project_agent_rows(project)` liefert Auswahl, Basis-Modell, Überschreibung
  und wirksames Modell.
- `project_agent_set(project, agent, selected, model)` ändert genau einen
  Agenten und schreibt nur die Projektdatei.
- `run_agent_selection(project, agent)` prüft die Abwahl und liefert die
  Modellüberschreibung.
- `cmd_run` bricht bei einem abgewählten Agenten vor tmux ab und übergibt die
  Überschreibung als zusätzliches Argument an den Läufer.

### Paketläufer (`bin/vibe-run.sh`)

- Neuer optionaler dritter Parameter `[modell]` (alternativ `VIBE_MODEL`).
- Das Modell wird gegen `^[A-Za-z0-9][A-Za-z0-9._:/@+-]*$` geprüft und
  ausschließlich als Array-Argument an `opencode run --model ...` übergeben;
  es wird nie über eine Shell ausgewertet.
- Agentendateien werden nicht verändert; andere Projekte sehen die
  Überschreibung nicht.

### HTTP-API (`bin/vibe-web.py`)

- `GET /api/project-agents?name=<projekt>` liefert Projekt, Agentenzeilen,
  Modellliste und Fehlerzustand.
- `POST /api/project-agents` mit `{"name", "agent", "selected", "model"}` ändert
  Auswahl und/oder Überschreibung. 409 bei gleichzeitiger Änderung, 400 bei
  ungültigen Eingaben.
- `POST /api/agent` mit `action=save` wendet zusätzlich übergebenes `values`
  über `agent_render_fields` auf den Rohtext an, bevor geschrieben wird. Die
  Oberfläche sendet nur geänderte Felder.

### Oberfläche (`PAGE`)

- `projectAgentsCard(name)` im Reiter „Einstellungen“; Zeilen tragen
  `data-project-agent="<name>"` und `data-selected="ja|nein"`.
- Kontrollkästchen `aria-label="Agent <name> auswählen"`, Modellauswahl
  `aria-label="Modell für <name>"`.
- `agentForm` merkt sich den Ausgangsstand der Formularfelder und sendet beim
  Speichern nur die Differenz als `values`.

## Grenzen

- Die Auswahl gilt je Projekt, nicht je Lauf. Sie wird beim Start geprüft; ein
  bereits laufender Agent wird nicht nachträglich abgewählt.
- Die Modellüberschreibung ersetzt keine Verfügbarkeitsprüfung. Ob das Modell
  beim Anbieter existiert, prüft opencode beim Lauf; die Oberfläche zeigt die
  bekannten Modelle als Auswahl, akzeptiert aber auch ein eingetragenes Modell.
- Es gibt keine projektübergreifende Auswertung, welches Modell ein Agent in
  welchem Projekt verwendet; dafür dient die Projektansicht.
- Ein Agent, der nur in einem anderen Projekt existiert, ist in diesem Projekt
  nicht auswählbar. Das entspricht der opencode-Sicht auf das Projekt.
- Die Datei wird nicht automatisch bereinigt. Bleibt ein Agent in
  `deaktiviert` oder `modelle` stehen, obwohl seine Agentendatei entfernt wurde,
  bleibt der Eintrag wirkungslos erhalten, bis der Nutzer ihn ändert.
