# AP22 — New vibe UI (Neuaufbau der Weboberfläche)

- **Arbeitspaket:** AP22 „New vibe ui“ (`TICKETS.md`): Rebuild der UI von Grund
  auf für die Hauptzielgruppe (nicht-/semi-technische Nutzer), alte UI bleibt
  als Option erhalten (standardmäßig aus), CLI-Parität als Qualitätskriterium.
- **Paketbranch:** `feature/m0p/ap22` (Basis `f49940d`).
- **Stand des Vertrags:** 2026-11-20 — dieses Dokument ist die verbindliche
  Vorgabe (DOM-Vertrag, API-Zusätze, Paritätsmatrix) für Tests, Implementierung
  und Review. Validierungsergebnisse werden am Ende ergänzt.

## Ziel und Zielgruppe

Die bestehende Oberfläche ist funktional gewachsen, aber für Endnutzer
überfrachtet. AP22 baut eine **komplett neue UI** (Vanilla HTML/CSS/JS, kein
Build-Schritt, ohne Framework) mit Fokus auf Projekt-/Produktsteuerung:

- Übersicht über alle Projekte/Produkte, Projektdetail, Arbeitspakete im
  Produktowner-Stil, Anlegen von Arbeitspaketen, Bugs, Feedback.
- Agenten einfach erstellen (geführter Wizard) und verwalten (alle Details auf
  einer Seite), einfach Projekte zuordnen.
- Ergebnisse, Probleme, Warnungen transparent, aber nicht störend
  (Benachrichtigungszentrale + Toasts).
- Führung durch die UI (Einstiegshinweise, Wizards, sinnvolle Leerzustände),
  wenige Klicks zu wichtigen Zielen, keine überladenen Bildschirme.
- Responsiv (Desktop/Tablet/Mobile), Hell-/Dunkelmodus, dezente Animationen
  (abschaltbar), Barrierefreiheit (Tastatur, ARIA, Skip-Link).
- Technische Funktionen sind **standardmäßig verborgen** und über
  Feature-Schalter in den Einstellungen einblendbar.
- **Keine Änderung des funktionalen Verhaltens**: alle bestehenden API-Endpunkte
  und Services bleiben unverändert; die neue UI konsumiert sie nur. Fehlende
  UI-Paritäten zu CLI-Einstellungen erhalten schlanke, neue lesende/schreibende
  Endpunkte über die bestehenden Services (siehe „Neue API-Endpunkte“).

## Feste Entscheidungen (Koordinator, autonom dokumentiert)

1. **Routing:** `/` liefert die neue UI (Standard). `/classic` liefert die alte
   UI vollständig und dauerhaft erreichbar (eigene HTML-Datei, unveränderte
   alte app.js/styles.css). Die neue UI verlinkt `/classic` in den
   Einstellungen („Klassische Oberfläche öffnen“). Damit ist die alte UI eine
   Option, die standardmäßig nicht aktiv ist — wie vom Ticket gefordert.
2. **Technik:** reine statische Dateien (HTML/CSS/JS) ohne Build-Schritt und
   ohne Fremd-Bibliotheken; Server bleibt Python-Standardbibliothek. Grund:
   Installations- und Wartungsmodell des Projekts (Setup kopiert Dateien,
   `node --check` genügt als Syntaxprüfung).
3. **Dateistruktur (neue Dateien, Manifestbereich `bin/web/`):**
   - `bin/web/index.html` — neue Shell (ersetzt die bisherige Datei gleichen
     Namens; alter Inhalt wandert nach classic.html).
   - `bin/web/classic.html` — alte Shell (inhaltlich die bisherige index.html).
   - `bin/web/nova.css` — Design-System der neuen UI (Tokens, Komponenten,
     Hell/Dunkel, responsiv, Animationen).
   - `bin/web/nova-core.js` — Boot, Auth (`#t=`→Session-Cookie), API-Helfer,
     Router (Hash), Theme/Animation/Feature-Schalter, Toasts, Glocke, i18n.
   - `bin/web/nova-home.js` — Startseite (Projektübersicht, Neuanlage, Ordner,
     Auschecken, Einstiegshinweise).
   - `bin/web/nova-project.js` — Projektansicht (Überblick, Arbeit, Assistent,
     Projekteinstellungen).
   - `bin/web/nova-output.js` — Live-Ausgabe (Hauptagent, Subagenten,
     Steuern, Fortsetzen).
   - `bin/web/nova-agents.js` — Agenten (Liste, Wizard, Ein-Seiten-Editor,
     Projektzuordnung).
   - `bin/web/nova-activity.js` — Aktivität (Läufe, Sessions, Fragen).
   - `bin/web/nova-settings.js` — Einstellungen (Erscheinung, Sprache, Zugriff,
     Feature-Schalter, erweiterte Bereiche).
   - `bin/web/i18n.js` — erweitert um die neuen Schlüssel (en/de vollständig).
   - Alte Dateien `app.js`, `styles.css`, `i18n.js` bleiben inhaltlich
     unverändert (nur i18n.js wächst um neue Schlüssel).
4. **Clientseitige Präferenzen (localStorage, je Browser):** Theme
   (`nv-theme`: `light`|`dark`|`auto`, Default `light`), Animationen
   (`nv-animations`: `on`|`off`, Default `on`, automatisch `off` bei
   `prefers-reduced-motion`), Feature-Schalter (`nv-features`: JSON-Objekt,
   Default alle aus), Einstiegshinweis (`nv-guide-dismissed`). Die **Sprache
   bleibt global serverseitig** (AP21-Vertrag: `ui.json`, `/api/language`).
5. **Feature-Schalter (alle standardmäßig aus):** `github`, `models`,
   `profiles`, `mcp`, `costs`, `harness`, `limits`, `gates`, `env`, `sandbox`,
   `writeaccess`, `agentsfile`, `priority`, `runs`. Sichtbar ohne Schalter:
   Projekte, Arbeit/Board, Ausgabe, Assistent, Agenten, Aktivität
   (Läufe/Sessions/Fragen), Einstellungen (Erscheinung/Sprache/Zugriff/
   Feature-Schalter/Klassisch-Link), Sessions-Limit, Benachrichtigungen.
6. **Board-Status:** Die API kennt nur `add`/`update`/`delete` für Tickets —
   Statuswechsel bleiben dem Nachweis-Workflow vorbehalten (kein Verhalten
   ändern!). Das Board zeigt vier ehrliche Spalten: Offen (`offen`), Blockiert
   (`BLOCKIERT`), Nachweis fehlt (`ohne Nachweis`), Erledigt (`erledigt`).
7. **Auth/Security unverändert:** `#t=`-Tausch gegen Session-Cookie über
   `POST /api/login`, `X-Token`/Cookie für API, Host-/Origin-Guard,
   POST-Whitelist. Neue Endpunkte folgen denselben Regeln (V-004/AP13).
8. **Render-Rennschutz** wie AP21 (Render-Token je View-Start; asynchrone
   Renderer prüfen vor dem Ersetzen, ob sie noch aktuell sind).
9. **Übersetzungen:** neue sichtbare Strings laufen ausschließlich über
   `tr()`/`bt()` (deutsche Quell-Schlüssel wie im Bestand); en/de vollständig.
   Formulierungen dürfen sich ändern (Ticket erlaubt Wortlautsänderungen),
   Backend-Antworten nicht.

## Server-Vertrag

### Seiten und statische Dateien

- `GET /` → neue Shell (`web/index.html`, Platzhalter `__VIBE_LANG__`,
  `__OPENCODE_URL__` wie bisher; eigener Seitencache).
- `GET /classic` → alte Shell (`web/classic.html`, gleiche Platzhalter; eigener
  Seitencache). Unbekannte Pfade bleiben 404.
- `STATIC_FILES` ergänzt: `/static/nova.css`, `/static/nova-core.js`,
  `/static/nova-home.js`, `/static/nova-project.js`, `/static/nova-output.js`,
  `/static/nova-agents.js`, `/static/nova-activity.js`, `/static/nova-settings.js`.
- `scripts/setup-vibe.py`: `WEB_FILES` um alle neuen Dateien ergänzen
  (`classic.html`, `nova.css`, `nova-*.js`), damit Installation und Prüfung
  (`test_web_files_cover_all_shipped_web_files`) vollständig bleiben.

### Neue API-Endpunkte (Parität, über bestehende Services)

Alle folgen dem Bestandsmuster: Auth erforderlich, Guard/Allowlist zentral,
Fachfehler als `200 {"ok": false, "message": …}` (wie `/api/ticket`),
strukturfehlerhafte Requests über den bestehenden `_read_json`-Fehlerweg.

- `GET /api/limits` → `{"ok":true,"mode":"stop"|"continue","problem":<str|null|"" bei gesunder Datei>,"lines":[<describe-Zeilen als Liste>]}`.
- `POST /api/limits` `{"action":"stop"|"continue"}` → speichert über
  `vibe_limits.save(PATHS.state, mode)` und liefert den neuen Zustand wie GET;
  unbekannte Aktion → `{"ok":false,"message":"Unbekannte Aktion"}`.
- `GET /api/gates` (optional `?name=<Projekt>`) →
  `{"ok":true,"project":<name|null>,"gates":{<key>:{"value":…,"origin":…}},"lines":[…]}`.
  (aus `vibe_gates.effective`, `describe`; **API-Schlüssel kleingeschrieben** wie
  `vibe_gates.DEFAULTS`: `repair_rounds`, `assist_rounds`, `retries`, `packages`,
  `override`; die Uppercase-Namen `REPAIR_ROUNDS` usw. sind nur die
  `.vibe/project.env`-Namen aus `PROJECT_ENV_KEYS`).
- `POST /api/gates` `{"key":…,"value":…,"project":…}` → global:
  `vibe_gates.validate` + `vibe_gates.save`; Projekt:
  `set_env_values(name, {PROJECT_ENV_KEYS[key]: wert})`, leerer Wert mit
  `project` entfernt den Projektwert. Unbekannte Schranke/ungültiger Wert →
  `{"ok":false,"message":…}` **ohne Schreibvorgang**. Antwort enthält die neue
  wirksame Ansicht wie GET.
- `GET /api/runs` → `{"ok":true,"records":[<Registerzeilen mit mindestens
  id,state,session,project>]}` (aus `run_registry().all()`, neueste zuerst).
- `POST /api/runs` `{"action":"prune"}` → exakt die CLI-Logik von
  `cmd_runs("prune")` über die Register-/Sitzungsprüfung (niemals wird eine
  tmux-Sitzung beendet): `{"ok":true,"ended":N,"running":N,"unknown":N,"lines":[…]}`.
  Unbekannte Aktion → `{"ok":false,"message":"Unbekannte Aktion"}`.
- `POST /api/emu` `{"action":"start"|"stop"}` → Spiegel von `cmd_emu`: nur mit
  Android-Projekt; Start/Stop des projektierten Skripts `scripts/emulator-<action>.sh`
  als Hintergrundprozess (Muster `vibe_services.verify_bg`), Ausgabe ins
  Laufprotokoll. Ohne Android-Projekt → `{"ok":false,"message":"Kein Android-Projekt vorhanden"}`.
- `GET /api/paths` → `{"ok":true,"paths":{…}}` — schreibfreie Pfadauflösung
  (`vibe_paths.resolve()` legt laut V-006-Tests keine Verzeichnisse an);
  Antworten enthalten keine Geheimnisse (nur Pfade/Ports).

## Paritätsmatrix: jedes CLI-Kommando → neue UI

Qualitätskriterium des Tickets: **jede CLI-Einstellung hat eine
UI-Entsprechung.** (CLI-Bestand: `docs/baseline.md` §5 plus AP17/AP18/AP19/AP21.)

| CLI | UI-Ort (neue UI) | API |
| --- | --- | --- |
| `vibe list` / `status` | Startseitenkarten / Projekt-Überblick | `/api/projects`, `/api/project` |
