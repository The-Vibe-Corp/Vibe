# AP03 — Überarbeitung der Agentenverwaltung

## Ziel

Die Agentenverwaltung wird für die allgemeine Ansicht und für die
Projekteinstellungen neu aufgebaut. Im Mittelpunkt stehen das einfache Anlegen
von Agenten, eine eindeutige Rolle je Agent, sichtbare Subagenten-Rechte und
ein Vibe-Standardagent, der ohne weitere Agenten alle Aufgaben übernimmt.

## Fachliches Verhalten

### Allgemeine Agentenverwaltung

- Die Liste zeigt ausschließlich systemweite Agenten
  (`~/.config/opencode/agents`). Projektlokale Agentendateien erscheinen dort
  nicht mehr.
- Jede Zeile macht sofort sichtbar:
  - **Aufgabe**: `description` des Agenten,
  - **Ergebnis**: das separat gepflegte Ergebnis,
  - **Subagenten**: `keine`, `alle` oder die ausdrücklich erlaubten Namen,
  - **Standardmodell**: das `model` aus der Agentendatei.
- Über die Auswahl **Rolle** lässt sich je Agent `coder`, `reviewer` oder
  `vibe` setzen bzw. entfernen. Die Rolle wird in `profiles.json` unter
  `rollen` gespeichert.
- Es kann immer nur einen Agenten mit der Rolle `vibe` geben. Der letzte
  Vibe-Agent kann nicht entfernt oder auf eine andere Rolle umgestellt werden,
  solange kein Ersatz zugewiesen ist.
- Ein Vibe-Agent ohne Modell wird in der Oberfläche als **nicht konfiguriert**
  markiert. Ein Projektlauf bricht in diesem Fall mit einer verständlichen
  Meldung ab. Ist kein anderer Agent konfiguriert, verwendet `vibe` den
  Vibe-Agenten.

### Agenteneditor

Der Editor bietet zusätzlich zu den bisherigen strukturierten Feldern
(`Beschreibung`, `Modus`, `Modell`, `Rechte`, `Temperatur`, `Max. Schritte`,
`Prompt`):

- **Rolle** (nur systemweit),
- **Ergebnis** (wird nicht in die Agentendatei geschrieben),
- **Subagenten-Rechte** mit den Stufen `keine`, `ausgewählt` und `alle`; bei
  `ausgewählt` erscheint je systemweitem Agent eine Checkbox,
- **Prompt-Gerüst**: erzeugt aus Aufgabe (Beschreibung) und Ergebnis einen
  Prompt mit `## Aufgabe`, `## Ergebnis` und `## Grenzen`. Die Aufgabe steht
  im Mittelpunkt; der Agent entscheidet Ausführung und Detailtiefe selbst,
  aber nur innerhalb seines eigenen Bereichs.

Beim Speichern werden nur geänderte strukturierte Felder übernommen. Freie
Rohtextänderungen an anderen Stellen bleiben erhalten.

### Hierarchie und Berechtigungen

- `permission.task` wird als Modus gelesen:
  - `task: allow` → `alle`,
  - fehlender Eintrag oder `deny` → `keine`,
  - Objekt mit `"*": deny` und `name: allow` → `ausgewählt`.
- Erlaubte Subagenten müssen existieren, systemweit sein und den Modus
  `subagent` oder `all` besitzen. Zyklen werden abgelehnt. Der Selbstbezug
  ist seit F32 für Agenten außer dem Vibe-Agenten ausdrücklich erlaubt
  (Opt-in, siehe `docs/features/F32.md`).
- Die Rechte werden als YAML-Block geschrieben; alle anderen Frontmatter-Zeilen
  und der Prompt bleiben unverändert.

### Projekte

- Projekte dürfen ausschließlich systemweite Agenten verwenden.
- Ohne eigene Konfiguration ist nur der Vibe-Agent aktiv. Weitere Agenten sind
  vorhanden, aber standardmäßig ausgeblendet. Eine Checkbox
  `Nicht konfigurierte Agenten anzeigen` blendet sie ein.
- Die Projektseite zeigt Aufgabe, Ergebnis, Subagenten und wirksames Modell.
- Je Projekt und Agent kann nur das Modell überschrieben werden. Die
  Überschreibung ändert weder die Agentendatei noch andere Projekte.
- Die Projektkonfiguration liegt in `<Projekt>/.vibe/agents.json` in Version 2:

  ```json
  {
    "version": 2,
    "aktiv": ["vibe-agent", "tester"],
    "modelle": {"tester": "anbieter/modell"}
  }
  ```

  Version 1 (`deaktiviert`) wird beim Lesen verlustarm migriert: alle nicht
  deaktivierten systemweiten Agenten werden aktiv, Modellüberschreibungen
  bleiben erhalten, der Vibe-Agent wird ergänzt.

## Technische Umsetzung

### Backend (`bin/vibe`)

| Funktion | Aufgabe |
| --- | --- |
| `agent_meta_load` / `agent_meta_save` / `agent_result` / `agent_result_set` | Ergebnis je Agent in `$VIBE_STATE/agent-meta.json`, getrennt von der Agentendatei |
| `agent_role_set` / `vibe_agent_name` / `vibe_agent_status` | Rollen in `profiles.json`, Eindeutigkeit des Vibe-Agenten, Modellstatus |
| `agent_task_policy` | liest `permission.task` als `all`/`none`/`custom` |
| `agent_validate_hierarchy` | prüft Existenz, Systemweite, Modus und Zyklen; Selbstaufruf seit F32 als Opt-in erlaubt, außer für den Vibe-Agenten |
| `agent_render_task` | schreibt den `task`-Block, ohne andere Zeilen zu verändern |
| `agent_prompt_scaffold` | erzeugt das Prompt-Gerüst |
| `project_agents_*` | Version 2 mit `aktiv`/`modelle`, Migration von Version 1 |
| `cmd_run` | bricht ohne definierten bzw. konfigurierten Vibe-Agenten ab |

`agents_all` und `project_agent_rows` liefern zusätzlich `result`, `role`,
`is_vibe`, `model_missing`, `allowed_agents`, `task_mode`, `configured` und
`selected`.

### Web-API (`bin/vibe-web.py`)

- `POST /api/agent` mit `action: save` akzeptiert zusätzlich `result`,
  `task_allowed` (Liste), `task_all` (bool) und `role`.
  Alle Werte werden **vor** dem Schreiben geprüft; ungültige Eingaben
  verändern die Agentendatei nicht.
- `POST /api/agent` mit `action: role` setzt nur die Rolle.
- `POST /api/agent` mit `action: scaffold` liefert das Prompt-Gerüst zurück und
  schreibt nichts.

### Oberfläche (`bin/web/app.js`)

- `agents()` zeigt den Vibe-Status (`#vibe-status`) und die neue globale
  Agentenliste.
- `agentForm()` enthält Rolle, Ergebnis, Subagenten-Rechte und das
  Prompt-Gerüst. Ein laufendes Speichern sperrt den Speichern-Knopf, damit kein
  zweiter Schreibvorgang mit veralteter Prüfsumme startet.
- `projectAgentsCard()` zeigt standardmäßig nur konfigurierte Agenten, bietet
  das Einblenden der übrigen und schreibt Auswahl und Modell getrennt.
- `profilesCard()` zeigt die Rollenzuordnung nur noch lesend an; gesetzt wird
  sie in der Agentenliste. Damit gibt es genau einen validierten Schreibweg.

## Tests

Die Fälle wurden aus Arbeitspaket und `SPEC.md` abgeleitet:

- `tests/unit/test_ap03_agent_management.py`: Rollen, Vibe-Status, Lauf-Sperre,
  Metadaten, Hierarchie/Zyklen, Projektkonfiguration Version 2 und Migration,
  Prompt-Gerüst, UI-Daten, atomare API.
- `tests/browser/test_ap03_agents_ui.py`: allgemeine Liste, Rollenwechsel,
  Editor (Ergebnis/Rolle/Rechte), Prompt-Gerüst, Projekteinstellungen,
  Screenshots.
- `tests/browser/test_agents_ui.py`, `tests/browser/test_project_agents_ui.py`
  und `tests/unit/test_project_agents.py`: an AP03 angepasste
  Regressionsfälle.

**Einschränkung des Nachweises:** Der in `.vibe/project.env` konfigurierte
Test-Agent (`TESTER=test-agent`) konnte in dieser Umgebung nicht über `Task`
aufgerufen werden; die Plattform verweigerte den Aufruf mit
`Permission denied: subagent`. Die genannten Testdateien stammen daher nicht
aus einem in dieser Sitzung nachweisbaren unabhängigen Test-Agentenlauf.
Zusätzlich wurden in dieser Sitzung drei Testfälle vom Koordinator angepasst:
der neue Vorrangtest für den Vibe-Agenten, die Race-Beseitigung im
Projekt-Editor-Test und die Umstellung des Schreibrechte-Tests auf den
globalen Editor. Der unabhängige Code-Reviewer muss diese Einschränkung
bewerten; sie wird hier offen ausgewiesen und nicht als Test-Agent-Nachweis
ausgegeben. Die Tests enthalten echte Zusicherungen; es wurden keine
Prüfungen abgeschwächt, übersprungen oder gelöscht.

## Abweichung von SPEC.md

Offene Abweichung (Folgeentscheidung nötig): `SPEC.md` (Abschnitt „Agenten“)
nennt weiterhin global und projektspezifisch anzeigbare Agenten und Rollen
auch für projektspezifische Agenten. Das Arbeitspaket AP03 legt demgegenüber
ausdrücklich fest, dass Projekte nur systemweit definierte Agenten verwenden
und nur das Modell je Projekt ändern dürfen. Diese Arbeitspaket-Vorgabe ist
die neuere, genauere Anforderung und wird hier umgesetzt; `SPEC.md` wurde im
Rahmen von AP03 nicht geändert, weil das Arbeitspaket die fachliche Neufassung
nicht beauftragt. Die frühere Projektkopie (`agent_copy`) bleibt im Backend
für bestehende Aufrufer erhalten, wird aber nicht mehr über die Oberfläche
angeboten.

## Entscheidungen und Grenzen

- Das Ergebnis liegt bewusst außerhalb der Agentendatei. Opencode kennt kein
  solches Frontmatter-Feld; so bleibt jede Agentendatei gültig.
- Projekte erhalten keine eigenen Agentendateien mehr. Die frühere
  Kopierfunktion in Projekte wurde deshalb aus der Oberfläche entfernt; die
  Backend-Funktion `agent_copy` bleibt für bestehende Aufrufer erhalten.
- Die Rollen `coding-agent`/`tester` aus `project.env` bleiben unabhängig von
  den hier vergebenen Rollen `coder`/`reviewer`/`vibe`.
- Das Prompt-Gerüst ist eine aktive Formulierungshilfe, kein automatischer
  Modellaufruf. Es entstehen dabei keine Kosten.
- Solange noch kein Agent die Rolle `vibe` besitzt (Altbestand direkt nach dem
  Update), bleibt ein ausdrücklich per CLI oder `AGENT` gewählter systemweiter
  Agent startbar. Erst mit definiertem Vibe-Agenten greift die
  Projektauswahl und nicht konfigurierte Agenten werden abgelehnt. So bricht
  kein bestehendes Projekt allein durch das Update ab; die Rollenzuweisung
  bleibt die Voraussetzung für den Standardlauf ohne Agentenangabe.
- Ein definierter Vibe-Agent ohne Modell sperrt jeden Lauf, auch wenn in
  `project.env` noch ein alter `AGENT`-Eintrag steht. Diese Sperre wurde nach
  dem ersten Review mit dem Regressionstest
  `test_cmd_run_aborts_without_a_model_even_when_agent_is_set` abgesichert.
