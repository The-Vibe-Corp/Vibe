# V-016 — Dashboard- und opencode-Lebenszyklus getrennt prüfen

Stand: 2026-10-31
Ausgangscommit: `ec00695`
Arbeitsbranch: `feature/v-016-lebenszyklus`

## Ziel

Dashboard, opencode-Server und Agentenläufe liefen bisher in tmux-Sitzungen,
deren Namen sich aus dem Profil ableiten (`vibe-ui`, `vibe-server`). Beendet
wurde eine Sitzung allein über ihren Namen. Daraus folgten drei Fehler:

- `vibe ui stop` und der Knopf im Dashboard beendeten jede Sitzung dieses
  Namens — auch eine fremde, nicht von vibe gestartete Sitzung.
- `vibe server stop` und `vibe ui stop` waren nicht gegeneinander abgesichert:
  Ein gleichnamiges Projekt oder eine fremde Sitzung konnte getroffen werden.
- Ein belegter Port wurde nicht erkannt; das Dashboard startete in eine
  Sitzung, die sofort scheiterte, und ein beliebiger 200er auf dem
  opencode-Port galt als gesunder opencode-Server.

Dieses Arbeitspaket gibt jeder von vibe gestarteten Sitzung eine Markierung,
prüft vor dem Start Port und Identität des Dienstes und beendet beim Stoppen
ausschließlich die eigene Sitzung. Dashboard, opencode und Agentenläufe haben
damit getrennte Lebenszyklen.

## Lieferumfang

- `bin/vibe` — Markierung `VIBE_MANAGED`, Sitzungsprüfung, Portprüfung,
  strenge Health-Prüfungen, reservierte Laufschlüssel.
- `bin/vibe-web.py` — geordnetes Beenden über `STOP`, letzte SSE-Zeile,
  Signalbehandlung, nicht-daemonisierte Handler.
- `tests/unit/test_lifecycle.py` — 17 Abnahmetests.
- `tests/unit/test_opencode_adapter.py`, `tests/unit/test_vibe_paths.py` —
  an die verwaltete Sitzung angepasst.
- `docs/import-manifest.json` — Prüfsummen und Eintrag `V-016`.
- `docs/features/V-016.md` — diese Dokumentation.

## Fachliche Umsetzung

### Getrennte Lebenszyklen

| Aktion | Wirkung | Bleibt unberührt |
| --- | --- | --- |
| Dashboard beenden (`vibe ui stop`, Knopf, `/api/shutdown`, SIGTERM) | beendet nur die Dashboard-Sitzung | Agentenläufe, opencode-Server |
| opencode stoppen (`vibe server stop`) | beendet nur die opencode-Sitzung | Dashboard, Agentenläufe |
| Agentenlauf stoppen (`vibe stop <projekt>`) | beendet nur den gewählten Lauf | Dashboard, opencode-Server |

Ein geschlossener Browser-Tab beendet nichts: Der SSE-Stream endet, die
Hintergrundprozesse laufen weiter. Ein Neustart des Dashboards erzeugt eine
neue Instanzkennung, lässt Läufe und opencode aber unverändert.

### Nur verwaltete Sitzungen

Beim Anlegen setzt vibe die tmux-Umgebungsvariable `VIBE_MANAGED`:

| Sitzung | Wert |
| --- | --- |
| Agentenlauf | `run` |
| Dashboard | `ui` |
| opencode-Server | `server` |

Vor jedem Beenden wird die Markierung gelesen. Fehlt sie, gilt die Sitzung als
fremd und wird nicht beendet; die CLI endet mit einer Meldung, die „gehört
nicht“ enthält. Eine fehlende Auskunft der Attrappe (`unbekannt`) wird nur
beim bereits registrierten Lauf toleriert, nie bei einer fremden Sitzung.

### Reservierte Namen

Die Laufschlüssel `ui` und `server` sind für Dashboard und opencode reserviert.
Ein Projekt namens `ui` oder `server` erhält einen Fingerabdruck im
Laufschlüssel und kann die beiden Sitzungen nicht übernehmen.

### Port und Identität

Vor dem Start wird der Port geprüft:

- Lauscht bereits ein eigener, gesunder Dienst, wird nur die Adresse
  ausgegeben.
- Lauscht etwas anderes, bricht der Start mit „Port … ist belegt“ ab; es wird
  keine Sitzung angelegt.
- Eine vorhandene, aber nicht als vibe markierte Sitzung führt ebenfalls zum
  Abbruch.

Das Dashboard gilt nur als eigenes, wenn `/api/health` `app == "vibe"` meldet
und die `instance`-Kennung zur laufenden Laufzeit (`web.instance`) passt. Ein
fremder Dienst, der die Form nachahmt, wird dadurch nicht übernommen.

Der opencode-Server gilt nur als gesund, wenn `/global/health` ein JSON-Objekt
mit `healthy: true` und einer nicht leeren `version` liefert. Ein beliebiger
200er oder eine HTML-Seite zählt nicht.

### Sauberes Beenden des Dashboards

`bin/vibe-web.py` setzt beim Beenden das Ereignis `STOP`. Aktive SSE-Streams
prüfen es und senden als letzte Zeile `Dashboard wird beendet.`, statt bis zum
Verbindungsabbruch weiterzulaufen. `/api/shutdown`, SIGTERM, SIGHUP und SIGINT
lösen denselben Weg aus. Die Handler-Threads sind nicht mehr daemonisiert;
`server_close()` wartet auf sie, sodass der Prozess mit „vibe-web beendet.“
und Exitcode 0 endet.

## Tests

`tests/unit/test_lifecycle.py` (17 Tests) prüft mit echten, isolierten
tmux-Sitzungen (eigener `TMUX_TMPDIR`), einem echten Dashboard-Prozess auf
freien Ports und Attrappen für opencode:

- alle Kombinationen laufender Prozesse (Dashboard, opencode, Lauf) für jede
  Stopp-Aktion: nur das Ziel verschwindet;
- fremde Sitzungen mit gleichem Namen werden nicht beendet, auch nicht mit
  Registereintrag;
- der Start verweigert eine fremde Sitzung;
- Projekte `ui` und `server` erhalten eigene Laufschlüssel und Sitzungen;
- Startbefehle setzen die Markierung `run`, `ui`, `server`;
- belegter Port und fremder Dienst werden erkannt (Dashboard und opencode);
- Dashboard-Health verlangt App- und Instanzkennung;
- opencode-Status verlangt `healthy: true` und Version;
- Dashboard beenden (Knopf, `vibe ui stop`, SIGTERM) lässt Lauf und opencode
  am Leben und beendet den Stream mit der letzten Zeile;
- opencode stoppen lässt Dashboard und Lauf am Leben;
- geschlossener Browser-Tab lässt Dashboard und Lauf weiterlaufen;
- Neustart erhält Lauf und opencode, erzeugt aber eine neue Instanzkennung.

Es werden keine Modell-, Router-, Android- oder produktiven MCP-Aufrufe
ausgeführt.

## Grenzen

- Die Markierung ist eine tmux-Umgebungsvariable. Wird eine Sitzung von Hand
  mit `VIBE_MANAGED=ui` angelegt, gilt sie als verwaltet; das ist eine
  bewusste, dokumentierte Vertrauensgrenze für denselben Benutzer.
- Die Portprüfung ist eine Momentaufnahme. Zwischen Prüfung und Start kann
  ein anderer Prozess den Port belegen; der Start scheitert dann sichtbar,
  aber die Prüfung verhindert es nicht atomar.
- Die Instanzkennung schützt gegen einen fremden Dienst, der die
  Health-Form nachahmt, nicht gegen einen Angreifer mit Schreibzugriff auf
  die Laufzeitdateien.
- Der Test belegt das Verhalten auf Linux mit tmux 3.8; andere
  tmux-Versionen können `new-session -e` anders behandeln.
- Ein hartes `SIGKILL` auf das Dashboard kann keine letzte SSE-Zeile mehr
  senden; der Test deckt SIGTERM ab.
