## Ziel

Beim Anlegen eines neuen Arbeitspakets über die Oberfläche musste bisher eine
ID von Hand vergeben werden. F23 ändert das: Wird das ID-Feld leer gelassen,
vergibt das System selbst die nächste freie ID. Eine eigene ID bleibt
weiterhin zulässig, damit bestehende Projektschemata (z. B. `F18`, `V-001`)
erhalten bleiben.

Der Wortlaut der vorherigen SPEC („die ID vergibt der Nutzer") widersprach
dem geforderten Verhalten. Der Widerspruch wurde bewusst zugunsten des
angeforderten Verhaltens aufgelöst und SPEC.md im Abschnitt „Arbeitspakete
und Feedback" aktualisiert, damit die fachliche Vorgabe wieder deckungsgleich
ist.

## Fachliches Verhalten

- Formular „Neues Arbeitspaket": Das ID-Feld ist kein Pflichtfeld mehr.
  Beschriftung: „ID (automatisch vergeben, wenn leer)"; Platzhalter:
  „leer lassen: automatisch vergebene ID".
- Leeres Feld: Der Server legt das Arbeitspaket an und vergibt die ID
  automatisch als `AP1`, `AP2`, … Der Toast nennt die tatsächlich vergebene
  ID, z. B. „AP1 angelegt".
- Bestehen in TICKETS.md bereits Einträge mit dem Präfix `AP` — auch als
  Nutzereingabe (etwa `AP3`) — wählt die Automatik die nächste freie Nummer
  über den bisherigen Maximalwert (hier `AP4`).
- Eine manuell eingegebene ID funktioniert unverändert, einschließlich der
  bisherigen Ablehnungen („Ungültige ID", „Titel fehlt", „Titel darf keinen
  Zeilenumbruch enthalten) und „Arbeitspaket existiert bereits".
- Fehlt TICKETS.md, bleibt auch bei leerem ID-Feld die alte Meldung
  „Keine TICKETS.md vorhanden"; die Datei wird nicht still erzeugt.
- API `POST /api/ticket` mit `action=add` akzeptiert fehlende oder leere
  `id` und liefert HTTP 200 mit der vergebenen ID in `message`. Für
  `update` und `delete` bleibt die ID Pflicht („ID fehlt").

## Technische Umsetzung

- `bin/vibe` — `add_ticket(name, tid, title, description="")`: Bei leerem
  `tid` prüft die Funktion, dass TICKETS.md existiert, und delegiert die
  Nummernvergabe an die vorhandene `_add_entry(...)` mit Präfix `AP`. Damit
  gilt die für Feedback (F/B) bewährte, kollisionsfreie Mechanik auch
  für Auto-IDs: Snapshot lesen, nächste freie Nummer bestimmen, atomar mit
  erwarteter Prüfsumme schreiben, bei `ConcurrentChangeError` erneut
  versuchen (20 Versuche, sonst verständlicher Fehler). Zurückgegeben wird
  der vollständige ID-String (`AP` + Nummer).
- `bin/vibe-web.py` — `POST /api/ticket` (`action=add`): Die Pflichtprüfung
  auf nicht-leere `id` (bisher `assert …, "ID fehlt"`) ist entfallen; die
  Erfolgsmeldung nutzt den von `add_ticket` zurückgegebenen ID-String, damit
  bei Automatik die vergebene ID erscheint. Update/Delete bleiben
  unverändert.
- `bin/web/app.js` — `ticketFormCard`: Neue Beschriftung und neuer
  Platzhalter des ID-Feldes. Struktur bleibt unverändert, bestehende
  Browser-Tests adressieren das Feld weiterhin über
  `input[aria-label='ID des Arbeitspakets']`.
- `docs/import-manifest.json` — Größen und Prüfsummen der geänderten,
  importierten Programmdateien (`bin/vibe`, `bin/vibe-web.py`,
  `bin/web/app.js`) nach der bisherigen Konvention jedes Pakets aktualisiert.
- `SPEC.md` — Abschnitt „Arbeitspakete und Feedback" auf das neue
  Verhalten aktualisiert (Automatik bei neuen AP, eigene ID bleibt
  möglich). Die Regel „IDs sind eindeutig; parallele Schreibvorgänge erzeugen
  keine Doppelungen" bleibt unverändert und gilt weiter.

## Betroffene Schnittstellen

| Schnittstelle | Änderung |

## Grenzen

- Die Auto-IDs nutzen für alle Projekte denselben Präfix `AP`. Ein Projekt
  mit einer gewachsenen ID-Konvention umgeht die Automatik, indem die ID
  eingetippt wird; die Automatik nummeriert ausschließlich `AP`-Einträge
  innerhalb desselben TICKETS.md, ohne andere Präfixe wie `F` oder `V-`
  zu berühren.
- Die Numerierung gilt je Projekt (TICKETS.md), nicht projektübergreifend.
- Der Browser-Test benötigt Playwright/Chromium; Umgebungen ohne Browser
  liefern diesen Nachweis nicht.
