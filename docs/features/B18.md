## Ziel

Die Harness-Auswahl wird robust: Ein nicht installierter Harness (Pi) kann
über die Oberfläche nicht mehr wirksam gewählt und gespeichert werden.
Standard und Initialwert bleiben opencode. Für nicht installierte Harnesses
gibt es einen Installieren-Knopf mit dem Installationsbefehl aus der
Registry, Rückmeldung und erneuter Prüfung.

Auslöser (19.11., 07:15): Alle AP-Versuche scheiterten mit
`Harness-Programm nicht gefunden: pi` (Exit 127), obwohl opencode installiert
und Standard ist; der gespeicherte Zustand blieb `pi`.

## Koordinator-Entscheidungen (2026-11-21, autonomer Modus)

1. **Beide Oberflächen:** Die Auswahl existiert in Nova
   (`bin/web/nova-settings.js`, `buildHarnessSection`) und Classic
   (`bin/web/app.js`, `harnessCard`). Beide erhalten dieselben Semantiken —
   der Backend-Guard in `POST /api/harness` schützt ohnehin beide; nur so
   ist „die Oberfläche“ durchgängig robust.
2. **Bestandsschutz statt Umschreiben:** Eine vorhandene `harness.json` mit
   `pi` (nicht installiert) wird nicht automatisch umgeschrieben — das Ticket
   fordert die Ablehnung neuer Speicherungen, kein Historieschrumpfen. Die
   Oberfläche zeigt den persistierten Wahrheitsstand (pi ausgewählt, Option
   deaktiviert, klare Meldung, Installieren-Knopf); nur NEUE `use`-Aufrufe
   werden abgelehnt.
3. **CLI außerhalb des Pakets:** `vibe harness use` (CLI) bleibt unverändert;
   das Ticket adressiert ausdrücklich die Oberfläche bzw. `POST /api/harness`
   (action=use). Keine Still-Erweiterung des Paketumfangs.

## Backend-Vertrag

### `bin/vibe_harness.py` — neue Funktion `install(name, ...)`

```python
def install(name, which=None, runner=None, timeout=300, environ=None):
```

* `definition(name)` validiert (unbekannter Harness → `HarnessError`).
* Installationsbefehl ausschließlich aus der Registry: `setup_plan(name)`
  liefert `install_command` (Pi: `npm install -g --ignore-scripts
  @earendil-works/pi-coding-agent`; opencode: `npm install -g
  opencode-ai`). Keine aufruferseitigen Argumente — kein beliebiger
  Befehlsaufruf.
* Bereits installiert (`which(binary)` findet das Programm): nichts ausführen,
  `{"harness", "code": 0, "output": "", "already": True, "probe": …}`.
* Sonst Befehl über die bestehende `_run`-Semantik ausführen (Runner in
  Tests injizierbar) und danach erneut `probe(name)` ausführen
  („erneute Prüfung“ auch serverseitig):
  `{"harness", "code", "output", "already": False, "probe": <probe-Ergebnis>}`.
* Deutsche, verständliche Rückgaben; keine Geheimnisse in `output`
  (`_short`-Kappung wie im Bestand).

### `bin/vibe-web.py` — `POST /api/harness`

* **action=use (Guard, Kern des Tickets):** Vor dem Speichern
  `vibe_harness.probe(chosen)` ausführen. `probe.installed == False` →
  **kein Speichern**: Antwort 400 mit
  `message = probe["message"] + " Auswahl nicht gespeichert."`
  (Beispiel: „Pi wurde nicht gefunden (pi; PATH prüfen oder installieren).
  Auswahl nicht gespeichert.“). `installed == True` → unverändert
  `write_selection` + „Gespeichert: …“.
* **action=install (NEU):** `{action:"install", harness:"pi"}` →
  `vibe_harness.install(...)` ausführen. Antwort:
  `{"ok": code==0, "message": "Installation abgeschlossen: <name>"
    | "Installation fehlgeschlagen (Exit <code>)"
    | "<Name> ist bereits installiert.",
    "install": {"code", "output", "already"}, "probe": <frisches probe>}`.
  Unbekannter Harness → bestehende HarnessError-Behandlung (ok:false).
* GET `/api/harness` bleibt unverändert (Status + supported).

### Bestandsschutz

`read_selection`/`write_selection`/`probe`/`setup_plan`/`status`/Registry
bleiben unverändert; bestehende API-Verträge (GET-Form, use bei
installiertem Harness, setup) brechen nicht. Initial-/Defaultwert bleibt
opencode (`read_selection`-Default).

## UI-Vertrag (Nova `nova-settings.js` UND Classic `app.js`)

* **Auswahl:** `select` je Option: nicht installiert → Option `disabled`
  mit Anzeige-Suffix „ (nicht installiert)“; installiert → unverändert
  „Name (id)“. Der persistierte Wert bleibt angezeigt/selected, auch wenn
  seine Option deaktiviert ist (Wahrheitsstand, Entscheidung 2).
* **Klarer Status:** die Statuszeilen zeigen je Harness
  „Installiert“/„Nicht installiert“ (Bestandsklassen `nv-ok`/`nv-bad`;
  Classic: `ok`/`bad`), Hinweis, offizielle Anleitung und den
  Einrichtungsplan (Installationsbefehl) — wie bisher sichtbar.
* **Installieren-Knopf** je NICHT installiertem Harness:
  * Nova: `button[data-nv-action="harness-install"][data-nv-harness="<id>"]`
    mit Text „Installieren“ in der Statuszeile des Harnesses.
  * Classic: `button.harness-install[data-harness="<id>"]`
    (id `harness-install-<id>`).
  * Klick → `POST /api/harness {action:"install", harness:"<id>"}`; danach
    erneuter `GET /api/harness` und Neuzeichnen: Rückmeldung im Feedback-
    Bereich — Nova `div[data-nv-harness-install-feedback]`, Classic
    `div#harness-install-feedback` (`[hidden]` bis zur ersten Rückmeldung) —
    mit Erfolg/Misserfolg und frischem Status; bei Erfolg wird die Option
    aktiviert und der Knopf verschwindet.
* **Übernehmen-Knopf** (use): bei Ablehnung zeigt die Fehlerbox die
  Backend-Meldung; Auswahl-Anzeige wird auf den persistierten Wert
  zurückgesetzt (frischer `GET /api/harness`), damit Anzeige und
  `harness.json` nie auseinanderlaufen. Bei Erfolg unverändert: Toast +
  Neuzeichnen aus der Server-Antwort/dem frischen GET (persistierter
  Zustand, nicht lokaler Wunschzustand).
* Beide Karten bauen weiter DOM nur mit `el()`/Textknoten (kein innerHTML
  mit dynamischen Inhalten); Nova nutzt `tr()`, Classic das Bestands-`tr()`.

## Testfälle (Test-Agent, Rotphase vor Implementierung)

Browser (`tests/browser/test_b18_harness_ui.py`; Muster
`tests/browser/test_ap04_harness_ui.py` — echte `bin/vibe-web.py`-Instanz
auf Loopback, Fake-Binaries im temporären `PATH`, keine Modellaufrufe):

1. **opencode-Default:** frischer Zustand ohne `harness.json` → Nova- und
   Classic-Auswahl zeigen `opencode`; Status „Installiert“ (Fake-opencode).
2. **Deaktivierte Auswahl:** `pi` fehlt im PATH → Nova-Option `pi` trägt
   `disabled` und „(nicht installiert)“, Statuszeile „Nicht installiert“,
   Installieren-Knopf vorhanden mit dem Registry-Befehl im Textumfeld;
   Classic entsprechend (`#harness-select` Option disabled,
   `harness-install`-Knopf).
3. **Ablehnung:** `POST /api/harness {action:"use", harness:"pi"}` → 400,
   Meldung enthält „Auswahl nicht gespeichert“; `harness.json` bleibt
   danach ohne `pi` (bzw. unverändert); UI-Übernehmen-Knopf mit
   deaktivierter pi-Option nicht erfolgreich auslösbar.
4. **Installationspfad:** Fake-`npm` im PATH legt bei Aufruf des
   Registry-Befehls die Fake-`pi`-Binary an → Klick auf „Installieren“
   liefert Rückmeldung im Feedback-Bereich; erneute Prüfung: pi-Option
   aktiviert, Status „Installiert“, Knopf verschwunden (Nova + Classic).
5. **Persistenter Zustand:** Wechsel zu (jetzt installiertem) `pi` →
   `GET /api/harness` meldet `selected: "pi"`, `harness.json` enthält `pi`,
   Neuladen der Ansicht zeigt weiterhin `pi` (Anzeige == Datei).

Unit (`tests/unit/test_b18_harness.py`; Runner/Which-Injektion wie
`tests/unit/test_ap04_harness.py`):

6. `install()` mit fehlendem `npm` (Runner liefert 127) → `code == 127`,
   Probe bleibt „missing“/nicht installiert.
7. `install()` mit Erfolgs-Runner → `code == 0`, `already == False`,
   anschließendes Probe „ready“ (erneute Prüfung serverseitig).
8. `install()` für bereits installierten Harness (which findet Binary) →
   `already == True`, kein Befehlauf, `code == 0`.
9. `install()` mit unbekanntem Harness → `HarnessError`.
10. Guard-Nachweis auf API-Ebene über Browser-Fall 3 (kein separates
    Unit-Framework für den Handler nötig — die Schranke lebt im Handler).
