# V-019 — Frontend und Backend schrittweise modularisieren

Stand: 2026-11-03

## Prüfumgebung

Der Prüfcontainer stellt `/tmp` und das Repository nur lesend bereit; schreibbar
ist allein `/tmp/opencode`. Außerdem exportiert die Agentenumgebung selbst
`SANDBOX`, `SANDBOX_TOOLS` und `VIBE_*`. Beides verfälscht Tests, die einen
eigenen `VIBE`-Ordner und eine ungesetzte Sandbox erwarten. Die vollständige
Prüfung lief deshalb in einem bubblewrap-Namespace mit schreibbarem `tmpfs` auf
`/tmp`, ohne geerbte `SANDBOX`-/`VIBE_*`-Variablen und mit dem Arbeitsbaum unter
`/tmp/work` (außerhalb des vom Sandbox-Modul erlaubten `/tmp/opencode`):

```
env -u SANDBOX -u SANDBOX_TOOLS -u TMPDIR -u VIBE_* \
  bwrap --dev-bind / / --tmpfs /tmp --dir /tmp/work \
  --bind <arbeitsbaum> /tmp/work bash -c 'cd /tmp/work && bash scripts/verify.sh full'
```

Ohne diese Trennung schlagen vorhandene Tests aus Umgebungsgründen fehl
(`SANDBOX` aus der Agentenumgebung, `web.token` unter dem erlaubten
`/tmp/opencode`). Mit ihr ist die Suite vollständig grün (siehe „Prüfungen“).

Der Arbeitsbaum des Repositories enthielt beim Start bereits nicht
committete Änderungen aus V-021 und V-022 sowie weitere Änderungen. Um keine
fremden Änderungen zu übernehmen oder zu überschreiben, wurde für dieses
Arbeitspaket ein eigener Worktree auf dem neuesten Stand mit den
Abhängigkeiten V-008 bis V-018 angelegt. Der Ausgangsstand ist deshalb
`d0c33cf` und nicht der ursprüngliche Branch `feature/v-017-...`.

## Ziel

Das Dashboard enthielt seine Ansichtslogik, die HTTP-Schicht und die gesamte
Oberfläche in einer einzigen Datei (`bin/vibe-web.py`, zuletzt rund 1400
Zeilen). Schreibende Aktionen riefen die CLI-Funktionen im Serverprozess auf
und fingen deren Ausgabe mit `contextlib.redirect_stdout` ab. Diese Umleitung
ist prozessweit: Bei parallelen Anfragen im `ThreadingHTTPServer` schrieben
zwei Threads in denselben globalen `sys.stdout`. Eine Anfrage konnte dadurch
die Ausgabe einer anderen erhalten, und nach dem Zurücksetzen blieb unter
Umständen der falsche Strom aktiv.

Dieses Arbeitspaket trennt die Schichten, ohne neue Funktionen einzuführen:

- gemeinsame Ansichts- und Aufrufdienste in `bin/vibe_services.py`,
- ein eigener Ausgabestrom je CLI-Aufruf statt globaler Umleitung,
- getrennte statische Dateien für HTML, CSS und JavaScript.

CLI und Web verwenden dieselben Fachfunktionen: Das Dashboard ruft für
Schreibaktionen unverändert die Kommando-Funktionen aus `bin/vibe` auf und
liest Ansichten über die gemeinsamen Dienste.

## Lieferumfang

- `bin/vibe_services.py` — gemeinsame Dienste: Projektansichten, Agenten-,
  Assistenten- und Wurzelansichten, Prüfstart sowie `capture()` für einen
  eigenen Ausgabestrom je Aufruf.
- `bin/vibe` — `cmd_run`, `cmd_stop`, `cmd_init`, `cmd_new`, `cmd_model` und
  `cmd_server` akzeptieren einen optionalen Ausgabestrom `out`. Ohne Angabe
  schreiben sie wie bisher auf `sys.stdout`. `col()` berücksichtigt den
  übergebenen Strom für die Farbentscheidung.
- `bin/vibe-web.py` — nur noch HTTP-Schicht, Authentifizierung, statische
  Auslieferung und Aufruf der Dienste. Keine eingebettete Seite und keine
  globale stdout-Umleitung mehr.
- `bin/web/index.html`, `bin/web/styles.css`, `bin/web/app.js` — getrennte
  statische Oberfläche. Der opencode-Link kommt aus einem Meta-Feld; das
  JavaScript bleibt unverändert und ohne serverseitige Textersetzung.
- `scripts/setup-vibe.py` — installiert, prüft und entfernt die statischen
  Webdateien mit; die Vollständigkeitserkennung berücksichtigt sie.
- `tests/unit/test_web_modularization.py` — neue Tests für getrennte
  Ausgabeströme, statische Auslieferung und parallele API-Anfragen.
- `tests/unit/test_web_ui_nonmodal.py` — liest die F11-Zusagen jetzt aus den
  getrennten Dateien; die Assertions bleiben inhaltlich unverändert.
- `tests/unit/web_page.py` — gemeinsame Testhilfe, die die ausgelieferte
  Oberfläche aus Startseite, Stylesheet und Skript zusammensetzt. Die
  Ansichtstests prüfen damit weiterhin die Inhalte, die der Browser erhält,
  statt sich auf eine eingebettete Seite zu verlassen.
- Sechs bestehende Ansichtstests (`test_feedback_capture`,
  `test_feedback_completed`, `test_feedback_edit_delete`,
  `test_project_guide`, `test_project_write_dirs`, `test_work_packages`)
  beziehen den Seiteninhalt über diese Hilfe. `test_questions` liest HTML und
  Skript aus den getrennten Dateien. Keine Assertion wurde entfernt oder
  abgeschwächt; die Hilfe verlangt zusätzlich für alle drei Dateien HTTP 200.
- `docs/import-manifest.json` — Prüfsummen der geänderten und neuen
  Programmdateien sowie Änderungseintrag V-019.
- `docs/features/V-019.md` — diese Dokumentation.

## Technische Umsetzung

### Gemeinsame Dienste

`bin/vibe_services.py` enthält die bisher in `vibe-web.py` eingebetteten
Ansichtsfunktionen:

| Funktion | Aufgabe |
| --- | --- |
| `project_row(vibe, name)` | Kurzansicht eines Projekts |
| `project_detail(vibe, paths, name)` | vollständige Projektansicht |
| `roots_info(vibe)` | Entwicklungsordner und gefundene Projekte |
| `agents_info(vibe)` | globale und Projekt-Agenten, Katalog, Profile |
| `project_agents_info(vibe, name)` | Agentenauswahl und Modelle eines Projekts |
| `guide_info(vibe, name)` | Zustand des Projektassistenten |
| `verify_bg(vibe, name, mode)` | Start einer Prüfung im Hintergrund |
| `tail(path, n)` | Protokollzeilen ohne Steuerzeichen |
| `capture(fn, *args)` | CLI-Aufruf mit eigenem Ausgabestrom |

Die Funktionen erhalten das geladene CLI-Modul als erstes Argument. Dadurch
gibt es keinen zweiten, konkurrierenden Import von `bin/vibe`, und die Dienste
lassen sich mit einem Ersatzmodul prüfen. Das CLI-Modul bleibt die einzige
Quelle der Fachlogik; das Web enthält keine eigene Projekt-, Agenten- oder
Berechtigungslogik mehr.

### Ausgabestrom je Aufruf

`capture()` legt für jeden Aufruf einen eigenen `io.StringIO` an und übergibt
ihn als `out` an die CLI-Funktion. Der globale `sys.stdout` wird weder gelesen
noch ersetzt. Das bisherige Verhalten bleibt erhalten:

- Erfolg liefert `(True, Ausgabe ohne ANSI-Steuerzeichen)`.
- `SystemExit` mit Meldung liefert `(False, Meldung)`.
- Eine Ausnahme liefert `(False, str(error))`.

Die sechs vom Dashboard aufgerufenen Kommandos schreiben ihre Ausgabe
konsequent auf den übergebenen Strom. Interne Hilfsfunktionen geben weiterhin
ihren Rückgabewert zurück und schreiben nicht selbst.

Der Nachweis des alten Fehlers ist reproduzierbar: Zwei Threads rufen eine
Funktion mit `print()` über die frühere globale Umleitung auf; ein Thread
hält die Umleitung und der andere schreibt hinein. Ergebnis des
Minimalbeispiels vor der Änderung:

```
RESULTS {'A': 'start A', 'B': 'start B\nend A'}
VERMISCHT
end B
```

Nach der Änderung erhält jeder Aufruf genau `start A\nend A` beziehungsweise
`start B\nend B`; der globale Strom bleibt unberührt.

### Statische Oberfläche

Die frühere Zeichenkette `PAGE` ist in drei Dateien aufgeteilt:

- `bin/web/index.html` — Gerüst mit Meta-Feld für den opencode-Link,
- `bin/web/styles.css` — das bisherige Stylesheet,
- `bin/web/app.js` — das bisherige Skript.

Der Server liefert nur die zwei freigegebenen Pfade `/static/styles.css` und
`/static/app.js`; alle anderen Pfade unter `/static/` antworten mit 404. Damit
sind Verzeichnisausbrüche und das Ausliefern beliebiger Dateien ausgeschlossen.
Die Dateien werden wie die Startseite ohne Token ausgeliefert, weil der Browser
sie beim Aufruf der Seite noch nicht mit einem Token anfordern kann.

Der opencode-Link stand bisher als Platzhalter im JavaScript. Jetzt steht er
als `content` im Meta-Feld `vibe-opencode-url`; `app.js` liest ihn beim Start.
Das Skript bleibt dadurch statisch und enthält keinen Platzhalter mehr.

### Installation

`scripts/setup-vibe.py` kennt neben `PROGRAM_FILES` jetzt `WEB_FILES` für die
drei statischen Dateien. Sie werden nach `_toolchain/bin/web/` installiert,
von `verify_installation()` geprüft, von `detect_existing()` für die
Vollständigkeit berücksichtigt und von `uninstall()` entfernt. Die bestehende
Sicherung, der Rollback und die Laufendsperre bleiben unverändert; der
Installationsplan verwendet weiterhin eine gemeinsame Quelle für Vorschau und
Ausführung.

## Verhalten

Es gibt keine neue Funktion. Alle Endpunkte, Meldungen, Berechtigungen und
Sicherheitsprüfungen bleiben unverändert. Geändert sind nur der Ort der
Ansichtslogik, der Weg der Ausgabe und die Auslieferung der Oberfläche.

## Tests

### Roter Nachweis vor der Umsetzung

`tests/unit/test_web_modularization.py` wurde gegen den Ausgangsstand `d0c33cf`
ausgeführt und schlug fehl, weil `bin/vibe_services.py` dort nicht existiert:

```
FileNotFoundError: [Errno 2] No such file or directory:
'/tmp/opencode/v019-base/bin/vibe_services.py'
Ran 0 tests in 0.000s
FAILED (errors=1)
```

Zusätzlich wurde der Ausgabefehler mit dem früheren `call()` und zwei Threads
reproduziert (beide halten ihre Umleitung, während beide ihre Endzeile
schreiben):

```
RESULTS {'A': (True, 'start A'), 'B': (True, 'start B\nend B\nend A')}
sys.stdout danach: StringIO
VERMISCHT
```

`A` verliert seine eigene Endzeile an den Puffer von `B`; der globale
`sys.stdout` bleibt anschließend auf einem toten `StringIO`. Mit `capture()`
aus dem Arbeitsstand liefert derselbe Ablauf:

```
RESULTS {'A': (True, 'start A\nend A'), 'B': (True, 'start B\nend B')}
```

### Neue und angepasste Tests

- `tests/unit/test_web_modularization.py` (8 Tests):
  - parallele `capture()`-Aufrufe mit einer Barriere vermischen keine Zeilen,
  - `capture()` schreibt nicht auf den globalen stdout,
  - `SystemExit` wird als Meldung zurückgegeben,
  - Startseite besteht aus getrennten Dateien ohne Inline-Style/-Skript,
  - CSS und JavaScript werden ohne Token mit passendem Content-Type geliefert,
  - unbekannte und ausbrechende `/static/`-Pfade antworten mit 404,
  - der opencode-Link erreicht die Seite ohne Platzhalter,
  - vier parallele `/api/init`-Anfragen erhalten jeweils nur ihre eigene
    Projektmeldung.
- `tests/unit/test_web_ui_nonmodal.py` (2 Tests) prüft die F11-Zusagen
  weiterhin, jetzt über HTML, CSS und JavaScript.
- `tests/unit/test_install_lifecycle.py` prüft zusätzlich, dass die
  Webdateien installiert, im Vollständigkeitscheck erkannt und beim Uninstall
  entfernt werden (38 Tests).
- Die sechs Ansichtstests und `test_questions.ServedPageTest` prüfen
  unverändert dieselben sichtbaren Texte und Endpunkte. Der erste
  vollständige Lauf zeigte, dass sie den eingebetteten Seitenquelltext
  erwarteten; die Anpassung bezieht den Inhalt deshalb über die ausgelieferten
  Dateien, ohne eine Zusage zu streichen.

## Grenzen

- Die Modularisierung bleibt bei der Standardbibliothek. Es wird kein
  Framework, kein Bundler und kein Build-Schritt eingeführt.
- Die statischen Dateien werden bei jeder Anfrage ohne Änderungsprüfung
  gelesen (HTML einmal je Prozess zwischengespeichert). Für ein lokales
  Einzelplatz-Dashboard ist das ausreichend; ein Cache mit ETag ist nicht Teil
  dieses Arbeitspakets.
- Schreibaktionen, die keine CLI-Kommando-Funktion haben (Feedback, Tickets,
  Rechte, Sandbox, Kosten, MCP, Assistent), rufen weiterhin die vorhandenen
  Fachfunktionen direkt auf. Sie schreiben nicht auf stdout; eine eigene
  Ausgabeumleitung ist dafür nicht nötig.
- `capture()` setzt voraus, dass die aufgerufene Funktion den Parameter `out`
  akzeptiert. Das ist für die sechs vom Dashboard verwendeten Kommandos durch
  die Tests abgedeckt; neue Aufrufe müssen diese Zusage einhalten.
- Die Trilium-Dokumentation ist über den vorhandenen MCP-Zugang abgelegt; die
  Notiz-ID steht in `docs/trilium-index.md`.
