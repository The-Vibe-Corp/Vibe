# V-017 — Bazzite-Starter produktionsreif integrieren

Stand: 2026-11-02
Ausgangscommit: `e53aaa5`
Arbeitsbranch: `feature/v-017-bazzite-starter-integration`

## Ziel

vibe war bisher nur über die Kommandozeile oder eine von Hand gepflegte
Installation erreichbar. Für den Start aus dem Bazzite-Anwendungsmenü fehlten
ein Starter, eine Desktopdatei, ein Symbol und ein Installer. Ein reiner
`xdg-open`-Aufruf hätte außerdem bei jedem Klick ein zweites Dashboard
gestartet, einen fremden Dienst auf dem Port übernommen oder den Container
unnötig betreten.

Dieses Arbeitspaket liefert eine dünne Host-Hülle:

- Läuft das Dashboard bereits, wird ausschließlich der Browser geöffnet.
- Läuft es nicht, wird der konfigurierte Distrobox-Container gestartet, das
  Dashboard gestartet, die Bereitschaft über `/api/health` abgewartet und
  danach der Browser geöffnet.
- Ein fremder Dienst auf dem Port wird erkannt und nicht übernommen.
- Mehrfachklicks erzeugen genau eine Dashboard-Instanz.
- Pfade mit Leerzeichen und Sonderzeichen bleiben getrennte Argumente.
- Die Menüaktion „Dashboard beenden“ beendet ausschließlich vibe.
- Fehler werden im Startmenü sichtbar gemacht und bereinigt protokolliert.

## Lieferumfang

- `scripts/vibe_starter.py` — Host-Starter (`start`, `stop`, `status`).
- `scripts/vibe-desktop.py` — Installer, Uninstaller und Zustandsprüfung.
- `scripts/install-vibe-desktop.sh`, `scripts/uninstall-vibe-desktop.sh` —
  stabile Einstiege für Dokumentation und Host-Aufrufe.
- `scripts/vibe.svg` — Symbol für den Menüeintrag.
- `tests/unit/test_bazzite_starter.py` — 37 Abnahmetests.
- `docs/features/V-017.md` — diese Dokumentation.
- `docs/features/V-017-bazzite.txt` — Protokoll der Host-Abnahme.
- `docs/baseline.md` — Bazzite-Zeilen auf den neuen Stand gebracht.

Die neuen Dateien liegen bewusst unter `scripts/` und werden vom Installer
zusammen mit `bin/vibe_paths.py` nach `$XDG_DATA_HOME/vibe/` kopiert. Dadurch
bleibt die Desktopintegration unabhängig von der reproduzierbaren
Installation aus V-018 und ändert weder `scripts/setup-vibe.py` noch die
produktive Installation.

## Fachliche Umsetzung

### Zustandserkennung

Der Starter fragt `http://<bind>:<port>/api/health` ab und unterscheidet drei
Zustände:

| Zustand | Bedingung | Reaktion |
| --- | --- | --- |
| `vibe` | HTTP 200, JSON-Objekt, `ok: true`, `app: "vibe"`, `instance` gleich der eigenen `web.instance` | nur Browser öffnen |
| `foreign` | irgendeine andere Antwort auf dem Port | abbrechen, nichts starten oder beenden |
| `absent` | keine Antwort / Verbindung abgelehnt | starten |

Die Instanzkennung verhindert, dass eine andere vibe-Instanz oder ein
nachgeahmter Health-Endpunkt übernommen wird. Fehlt die eigene
`web.instance`, gilt die Antwort nie als das eigene Dashboard.

### Start

1. Ein Dateischloss (`flock`) im Laufzeitordner serialisiert gleichzeitige
   Starter-Aufrufe. Zwei Klicks laufen nacheinander; der zweite sieht das
   bereits laufende Dashboard.
2. Bei `vibe` wird das Token aus `web.token` gelesen und der Browser mit
   `#t=<token>` geöffnet. Ein fehlendes Token führt zu einer sichtbaren
   Meldung statt zu einer kaputten URL.
3. Bei `absent` wird die vibe-CLI als Argumentliste aufgerufen:
   `distrobox enter --no-tty <container> -- env KEY=WERT … python3 <vibe> ui start`.
   `--no-tty` ist für den Start ohne Terminal erforderlich. Die aufgelösten
   Pfade und Ports werden als einzelne `KEY=WERT`-Argumente übergeben; eine
   Shell wertet den Befehl nicht aus.
4. Der Starter wartet bis `VIBE_START_TIMEOUT` (Standard 30 s) auf eine
   gültige Health-Antwort. Ein fremder Dienst während des Wartens bricht ab.
5. Erst danach wird das (gegebenenfalls neu erzeugte) Token gelesen und der
   Browser geöffnet.

Läuft der Starter bereits im Container (`/run/.containerenv`, `container` oder
`DISTROBOX_ENTER_PATH`), entfällt der Distrobox-Aufruf.

### Beenden

`stop` prüft zuerst den Zustand:

- `absent`: es wird nichts gestartet und kein Container betreten.
- `foreign`: es wird nichts beendet.
- `vibe`: nur dann wird `vibe ui stop` aufgerufen. Die vibe-CLI beendet
  ausschließlich die verwaltete Dashboard-Sitzung; opencode und Agentenläufe
  bleiben unberührt.

### Quoting

- Programmaufrufe verwenden ausschließlich Argumentlisten
  (`subprocess.run([...])`), nie `shell=True`.
- Pfade mit Leerzeichen, Umlauten, `$`, Apostroph und Klammern bleiben ein
  Argument.
- `VIBE_BROWSER` und `VIBE_NOTIFY` akzeptieren entweder einen vorhandenen
  ausführbaren Pfad (auch mit Leerzeichen) oder eine Befehlszeile mit
  Optionen.
- Die Desktopdatei quotet das `Exec`-Feld nach der Desktop-Entry-Spezifikation:
  doppelte Anführungszeichen bei Leerraum/Sonderzeichen, Escapes für `"`,
  `\`, `` ` `` und `$`, Verdopplung von `%`.

### Installation und Uninstall

Der Installer arbeitet ausschließlich benutzerbezogen unter
`$XDG_DATA_HOME` (Standard `~/.local/share`) und benötigt keine Root-Rechte.
Er schreibt atomar und installiert:

- `vibe/vibe_starter.py` (Modus 755) und `vibe/vibe_paths.py`,
- `icons/hicolor/scalable/apps/vibe.svg`,
- `applications/vibe.desktop` mit der Aktion `stop`,
- `vibe/install-manifest.json` mit SHA-256-Prüfsummen.

Ein vorhandener fremder Menüeintrag wird vor dem Ersetzen als
`vibe.desktop.bak-<zeitstempel>` gesichert. Ein erneuter Install erkennt die
eigenen, unveränderten Dateien anhand des Manifests und legt keine weiteren
Sicherungen an.

Der Uninstall entfernt nur Dateien, deren Prüfsumme noch dem Manifest
entspricht. Geänderte Dateien, fremde Menüeinträge, Projekte, Laufzeitdaten
und persönliche Einstellungen bleiben erhalten. Ein zweiter Uninstall ist
idempotent.

### Fehler sichtbar machen

Fehler werden auf stderr ausgegeben, über `notify-send` (oder `VIBE_NOTIFY`)
angezeigt und in `<runtime>/desktop-starter.log` protokolliert. Tokens werden
aus Meldungen und Logzeilen entfernt (`#t=…` und der konkrete Tokenwert).
Das Log wird mit Modus 600 angelegt.

## Tests

`tests/unit/test_bazzite_starter.py` (37 Tests) verwendet echte Prozesse,
einen echten HTTP-Server, echte tmux-Sitzungen mit eigenem `TMUX_TMPDIR` und
Attrappen für Browser, Notifier und Container:

- Health-Erkennung: echte vibe-Antwort, fremder Dienst, nachgeahmte Antwort
  mit falscher Instanz, fehlende Instanzdatei, Verbindung abgelehnt, echter
  HTTP-Server ohne vibe-Health.
- Start: laufendes Dashboard öffnet nur den Browser; fehlendes Dashboard
  startet Container und Browser; Container-Umgebung ohne Distrobox-Umweg;
  fremder Dienst blockiert; Tokenwechsel wird bei jedem Start gelesen;
  fehlendes Token wird gemeldet; Erfolg wird tokenfrei protokolliert.
- Beenden: nur `ui stop`, kein Containerstart bei `absent`, kein fremder
  Dienst.
- Quoting: Sonderzeichen im Arbeitsbereich, Browser- und Notifierpfad mit
  Leerzeichen, getrennte Argumente.
- Mehrfachklick: zwei parallele Starter erzeugen genau eine Dashboard-Sitzung
  und zwei Browseraufrufe.
- Echter Dashboard-Start ohne Attrappe: Start, zweiter Klick, Stop, Neustart
  mit neuem Token.
- Installer/Uninstaller: Dateien, Manifest, Modus, Sicherung fremder
  Desktopdateien, Uninstall nur unveränderter Dateien, idempotenter Uninstall,
  Status, Dry-Run, wiederholter Install, gültiges SVG, importierbarer
  installierter Starter, Stop-Aktion.

V-017 gehörende Änderung an `scripts/setup-vibe.py` (V-018) rot

installiertes `vibe_sandbox.py` abbrechen. Mit `bash scripts/verify.sh quick`
und `bash scripts/verify.sh full` allein im normalen Arbeitsbaum wären die
Ergebnisse durch diese Umgebung verfälscht, nicht durch V-017.

## Echte Bazzite-Abnahme

Die Abnahme lief auf dem Host (Bazzite) über `distrobox-host-exec`, mit einem
separaten Testcontainer `vibe-v017-accept`, dem Dev-Profil, Port 8788, einem
Arbeitsbereich mit Leerzeichen, Umlaut, `$`, Apostroph und Klammern sowie
Attrappen für Browser und Notifier. Die produktive Instanz (`vibe-ui`,
Port 8787, Container `android-dev`) blieb während der gesamten Abnahme
unverändert.

| Fall | Ergebnis |
| --- | --- |
| Container aus, Dashboard aus | Starter startet den Container, das Dashboard und öffnet den Browser mit Token |
| Dashboard läuft, zweiter Klick | nur Browser, keine zweite Sitzung, identische URL |
| Doppelklick (zwei parallele Starter) | genau eine Dashboard-Sitzung, zwei Browseraufrufe |
| Tokenwechsel nach Stop/Start | neues Token, neue URL, altes Token erscheint nicht |
| Fremder Dienst auf Port 8789 | Exit 1, Meldung „fremder Dienst“, kein Browser |
| Startfehler (CLI Exit 3) | Exit 1, stderr, Notifier, bereinigtes Log, kein Browser |
| Menüaktion stop | nur `vibe-ui-dev` beendet; `vibe-ui`, Port 8787 und Container bleiben |
| Stop ohne Dashboard | Exit 0, „vibe läuft nicht; nichts beendet.“ |
| Desktopdatei | `desktop-file-validate` Exit 0 für normale und für Pfade mit Leerzeichen, `$`, Apostroph und Klammern |

Der Testcontainer wurde nach der Abnahme gestoppt; die produktiven
tmux-Sitzungen `vibe-ui` und `vibe-vibe` sowie das Dashboard auf 8787 waren
danach weiterhin vorhanden.

Das vollständige Protokoll dieser Host-Abnahme liegt unter
`docs/features/V-017-bazzite.txt` (52 Zeilen, Ergebnis „0 Fehler“). Es zeigt
eingangs den Testcontainer als `Exited` und danach den vom Starter gestarteten
Zustand. Zusätzlich wurde die erzeugte Desktopdatei mit einem Datenverzeichnis
aus Leerzeichen, Umlaut, `$`, Apostroph, Klammern und `%` installiert;
`desktop-file-validate` endete mit Exit 0.

## Grenzen

- Der Starter prüft den Port als Momentaufnahme. Zwischen Health-Prüfung und
  Browseröffnung kann ein anderer Prozess den Port belegen; der Start scheitert
  dann sichtbar, aber nicht atomar.
- Die Instanzkennung schützt gegen einen fremden Dienst, der die Health-Form
  nachahmt, nicht gegen einen Angreifer mit Schreibzugriff auf die
  Laufzeitdateien.
- Der echte Container-aus/an-Fall wurde mit einem separaten Testcontainer
  geprüft. `android-dev` konnte nicht gestoppt werden, weil die laufende
  Entwicklungssitzung selbst darin läuft; das Verhalten von `distrobox enter`
  ist für beide Container dasselbe.
- Die Desktopdatei wird installiert, aber nicht in einer echten GNOME-Shell
  angeklickt. Die Abnahme prüft den Starter direkt und die erzeugte
  Desktopdatei statisch (Exec-Quoting, Aktion `stop`, Icon-Pfad).
- Ein fehlendes `python3` auf dem Host kann der Starter nicht melden, weil er
  dann selbst nicht startet. Bazzite liefert Python 3 im Basissystem.
- Die Bazzite-Abnahme verwendet Attrappen für Browser und Notifier, damit
  keine echten Fenster oder Benachrichtigungen nötig sind; die aufgerufenen
  Programme und Argumente werden dabei real ausgeführt.
