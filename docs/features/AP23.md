## Ticket-Text (verbindliche Grundlage)

> - [x] AP23 key management
>   Beschreibung: Look at this: https://infisical.com/platform/agent-vault.

>   Create a lightweight concept how to realize a save key management in vibe, so that keys never get leaked (for example for provider or github keys). The implement it. The Idea is hat in the future vibe will handle keys for github and also api keys for different agentic providers and then configure the selected harniss with this keys and providers, so that the user don't have to touch the harniss at all. and this can be configured through vibe.

## Zielbild

Vibe verwaltet die Zugangsdaten zentral („save key management"): GitHub-Tokens und API-Keys agentischer Provider liegen in einem geschützten Verwaltungsraum (Vault) und werden bei Bedarf in die Konfiguration des agentischen Harness (z. B. opencode) übernommen. Nutzer konfigurieren das Harness über vibe; das Harness selbst braucht keine manuelle Zugriffskonfiguration.

## Konzept

### Zustände (Design)

- `add` — Secret speichern (interaktiv: Name, Provider, Wert).
- `select` — Provider/Secret für den nächsten `vibe run` auswählen.
- `list` — Liste mit Maske (nur Präfix/Länge, nie Plaintext).
- `remove` — Secret löschen.

### Speicherformat (Design)

- `<state>/keys.json`: vault-Referenzen; Verschlüsselung AES-GCM, Schlüsselübergabe aus OS-Keyring oder Umgebungsvariable; Datei wird atomar geschrieben (Muster `write_text_atomic` aus `bin/vibe_packages.py`).

### Harness-Sync (Design)

- Startpfad `vibe run`: gewählte Secrets werden in die Harness-Config geschrieben (z. B. `auth.json` von opencode).
- Session-Ende: Harness-Config zurück auf „nicht konfiguriert" (Least Privilege).

### Hardening (Prinzipien, unabhängig von Umsetzung)

- Secrets niemals in Logs oder Protokollen (`scripts/check-no-secrets.py`-Heuristik: Private Keys, GitHub-Tokens, `sk-…`, Zugangsdaten-Zuweisungen).
- Secrets nicht in Commits/Repository; Commit-Scan gegen bekannte Muster.
- Datei-Rechte 0600 auf dem Vault, Parent-Verzeichnisse 0700.
- Local-Only-Vault: kein externer Transport, keine Netzwerknutzung.

## Entwurfsentscheidungen (dem Koordinator vorgestellt)

- OS-Keyring pro Plattform (macOS Keychain, Windows DPAPI, Linux libsecret/kwallet) mit Umgebungs-Fallback.
- Backup: keine; Rotation nur per Neuerzeugung des Vault-Schlüssels.

## Abhängigkeiten

Keine. (Nachbarschaften: AP21 i18n, V-003 Secure Development Environment, V-027 agent limits)

## Implementierung

### Dateien und Schnittstellen

- `bin/vibe_keys.py` (neu, nur Standardbibliothek): AES-128/192/256-GCM, Vault, Einträge, Harness-Sync, CLI.
- `bin/vibe`: `cmd_keys` mit `vibe keys add|select|list|remove`; Secret-Eingabe ohne `--secret` über `getpass` (nie als Argument), Standardprovider `generic`.
- `bin/vibe-run.sh`: `run_agent_in` ruft vor dem Agentenstart `sync` auf (Fehler → Abbruch mit Exit 2) und nach `wait` `sync --reset` (`|| true`).
- `docs/import-manifest.json`: Eintrag und Prüfsumme für `bin/vibe_keys.py`, aktualisierte Digests für `bin/vibe` und `bin/vibe-run.sh`, `aenderungen`-Eintrag AP23.

### Vault und Kryptografie

- `<state>/keys.json` (Version 1) enthält `entries` mit `id`, `name`, `provider`, `ciphertext`, `nonce`, `tag`, `created` und die Auswahl `selected`; Datei-Modus 0600, atomar geschrieben über `write_text_atomic` aus `bin/vibe_packages.py`.
- AES-GCM mit 96-Bit-Nonce (`secrets.token_bytes(12)`); AAD bindet `name` und `provider` an den Chiffretext, ein manipulierter Eintrag ist nicht entschlüsselbar. Das Tag wird mit `hmac.compare_digest` konstantzeitlich geprüft; bei Manipulation liefert `aes_gcm_decrypt` `None`.
- Der 32-Byte-Vault-Key kommt aus `VIBE_KEYS_VAULT_KEY` (Base64) oder über Linux `secret-tool lookup service vibe-keys user vibe-key-manager` (5 s Zeitgrenze, ohne stdin). Ein explizit übergebenes `environ` ist eine Sandbox-Grenze: ohne injizierten `runner` werden dort keine externen Prozesse gestartet.
- `list_entries` zeigt nur die ersten drei Zeichen und die Länge (z. B. `ghp… (35 Zeichen)`), niemals den Wert; ohne Vault-Key bleibt die Maske ohne Präfix.

### Sitzungsauswahl und Harness-Sync

- `select_entry` entschlüsselt das Secret einmalig und legt es als `<state>/selected.json` (0600, atomar) für den nächsten Lauf ab. Bei jedem `sync` wird – sofern der Vault-Key verfügbar ist – frisch aus dem Vault entschlüsselt; die Sitzungsdatei ist nur der Fallback für den Läuferpfad, in dem die `VIBE_*-Umgebung` bereinigt wird. `sync-reset` und `remove_entry` löschen sie.
- `sync` schreibt für `harness=opencode` in `auth.json` (Default `~/.local/share/opencode/auth.json`, überschreibbar mit `--auth-path`): `data[provider] = {"type": "api", "key": <secret>}`. Andere Provider bleiben erhalten; die Datei wird atomar und mit 0600 geschrieben, es bleiben keine `.tmp`-Reste.
- Leere Auswahl ist ein No-Op (Exit 0, keine Datei wird angelegt). Andere Harnesses (z. B. `pi`) werden mit klarer Meldung abgelehnt. Fehlt bei expliziter Umgebung der Vault-Key, meldet `sync` „Vault-Schlüssel nicht verfügbar" und liefert Exit 2.
- `sync_reset` entfernt nur den synchronisierten Provider und die Sitzungsdatei; der Vault und alle anderen Einträge bleiben unverändert.

### CLI

- `vibe keys add <name> [--provider P] [--secret S]` – speichern (ohne `--secret` versteckte Eingabe)
- `vibe keys select <name>` – für den nächsten `vibe run` auswählen
- `vibe keys list` – Name, Provider, Maske
- `vibe keys remove <name>` – löschen und Auswahl bereinigen
- Direkt aufrufbar: `python3 bin/vibe_keys.py sync|sync-reset --state <ordner> --harness opencode [--auth-path <pfad>]`; `sync --reset` ist der Alias für den Läufer. Exit 0 bei Erfolg, 2 bei Fehler.

### Hardening und Design-Entscheidungen

- Kein Secret in Vault-Klartext, Logs, Meldungen, Commits oder Prozessargumenten (Empfehlung: `getpass` statt `--secret`); keine Netzwerkzugriffe, der OS-Keyring wird nur lokal mit Zeitgrenze befragt.
- Reines Python-AES-GCM ohne Abhängigkeit: die Installation bleibt auf Standardbibliothek beschränkt; NIST-Vektoren und Manipulationsfälle sind Teil des Vertrags.
- Kein Backup und keine Rotation des Vault-Keys; ein Kompromittierungsfall erfordert die Neuerzeugung des Vaults und anschließendes erneutes Eintragen der Secrets.
- Die kurzlebige Sitzungsdatei ist ein bewusster Kompromiss: sie enthält genau ein Secret für genau einen Lauf, ist 0600 und wird beim Reset entfernt. Ein Sync direkt aus dem Vault ist jederzeit möglich, sobald der Vault-Key in der Umgebung verfügbar ist.
